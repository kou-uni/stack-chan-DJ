# 曲判定ロジックの振り返りと改善案

2026-09-08。一日かけて実機で追い込んだ結果と、そこから見えた改善の方向。

---

## 1. 今日やったことの棚卸し

| いじったもの | 結果 |
|---|---|
| 感度 0.5 → 0.9 → 0.3 | 音量に応じて**逆向き**に動かすのが正しいと判明 |
| 停止判定 1.4秒 → 2.2秒 → 4秒 | 実機の listen が30秒ごとに3秒切れるため、短いと誤判定 |
| 監視間隔 0.4秒 → 1.5秒 → 1.0秒 | **速いとコマンドが音声フレームを奪って検出を壊す** |
| `MIN_MOTION_CONFIDENCE` 0.35 → 0.12 | 実機のマイクではBPMが揺れて0.35に届かない |
| 音量(level)をスナップショットに追加 | 「静か」と「ブレイク中」を区別するため |
| 4秒ごとに首を止めて測る | **サーボ音を排除するため** |

**大きく効いたのは、パラメータではなく「測るものを変えた」3つだけ。**
音量の露出、聴き入る動作、`frames_dropped` の確認。
**残りは全部、汚れた入力の補正だった。**

## 2. 根本原因 ── 入力信号が悪い

実測値が全てを語っている。

| 音源 | マイクが拾うRMS |
|---|---|
| 静かな部屋 | 0.0035 |
| **音楽** | **0.06** |
| **サーボ** | **0.16** ← 音楽の2.7倍 |

**信号より雑音の方が大きい。** この状態で閾値を調整しても、原理的に分離できない。
しかも**サーボは拍に同期して鳴る**ので、雑音が「理想的な拍」の形をしている。

さらに検出器そのものが弱い。

```
threshold_ratio = 1.65    直近平均の1.65倍に跳ねた瞬間を「拍」とする
rise_ratio      = 1.18
refractory      = 0.24s
```

**広帯域のRMSが跳ねただけで拍とみなす。** これでは
音楽・話し声・拍手・サーボ・食器の音を区別できない。話し声は
モーラがほぼ等間隔なので、**BPM 150〜250 の「曲」として非常によく検出される。**

## 4. 改善案（効果の大きい順）

### ★A. DJの音を、空気ではなくデジタルで受け取る

**いちばん効く。** rekordbox の出力をループバックで直接受ける。

```
rekordbox ──▶ 複数出力装置 ─┬─▶ DDJ-FLX2（スピーカーへ）
                            └─▶ BlackHole（仮想入力）──▶ 自作の解析
```

これで**一撃で消える問題**：

- サーボ音（そもそも入らない）
- 話し声・拍手・食器（入らない）
- 音量依存（デジタルなので常に一定）
- 「聴き入る」ための首の停止（不要になる）
- 感度のチューニング（不要になる）

BlackHole は無料・オープンソース。**導入は15分。**

**代償**：「ロボットが部屋の音を聞いている」という物語は失われる。
→ イベントでは**両方積む**。普段はデジタル、見せ場だけマイク。

### ★B. テンポを推定せず、rekordbox から貰う（Ableton Link）

rekordbox は Ableton Link に対応している（Performance モードのみ）。
**BPMと拍の位置がネットワーク越しに正確に届く。** 推定が丸ごと不要になる。

`console.py` は既に **「拍の時計」と「振り付け」が分離**されている
（`pose.sync(bpm, age)` / `led.sync(...)`）ので、**供給元を差し替えるだけ**で載る。

**A と B を両方やると、音の解析が「鳴っているか」の判定だけになる。**

### B'. Mac の USB マイクを使う（Aが使えない会場向け）

Shure MV6 が既定の入力になっている。**スタックチャンから物理的に離せる**ので、
サーボ音の問題が消える。空気を伝わる音を聞く点は変わらないので、
「部屋の音を聞いている」物語も残る。**Aより弱いがマイク版の最善。**

### C. 低域だけを見る（マイクを使い続ける場合の最善策）

**キックは 50〜120 Hz。サーボの唸りは 1〜8 kHz。**
帯域通過フィルタを入れるだけで、SNRが逆転する。

**これ単体で「聴き入る」動作が不要になる可能性がある。**
実装は2次のバターワース1本。numpy があれば数十行。

### D. 検出方法を変える ── スペクトル・フラックス

いまは広帯域RMSの跳ね。**周波数ごとの変化量の総和（spectral flux）**にすると、
音量が変わらなくても「音色が切り替わった瞬間」を捉えられる。
音楽の onset 検出では標準的な手法で、**RMSより格段に強い。**

16kHz・1024点のFFTを 31回/秒。numpy なら負荷は無視できる。

### E. テンポ推定を自己相関にする

いまは**拍と拍の間隔の中央値**。1つ取りこぼすと倍・半分に飛ぶ
（実測で 99→84→79 と揺れた）。

**onset強度の包絡線を自己相関にかけ、BPM帯（85〜160）で最大を探す。**
取りこぼしや余分な検出に強い。**オクターブ補正**（65と出たら130に直す）も入れる。

### F. BPMの範囲を絞る

いまの既定は `bpm_min=60 / bpm_max=200`。**話し声のテンポ（150〜250）が入る。**
DJの曲は 100〜140 に収まるので、**範囲を絞るだけで話し声を原理的に弾ける。**
設定1つで効く、いちばん安い対策。

### G. 自分の動きを差し引く

サーボへ指令を出した時刻は**こちらが知っている**。
その前後 ±80ms の onset を無視するだけで、自己雑音の大半が消える。
Cと組み合わせれば、聴き入る動作は完全に不要になるかもしれない。

---

## 5. 推奨する順番

1. **F（BPM範囲を絞る）** ── 設定1つ。今すぐ効く
2. **A（デジタル入力）** ── 15分。問題群が丸ごと消える
3. **B（Ableton Link）** ── 推定そのものを廃止する
4. C・D・E ── マイク運用を続ける場合の本格改修
5. G ── Cの補助

**イベントまで21日。1と2で当日の信頼性はほぼ確保できる。**
3以降は「時間が余ったら」で構わない。

## 6. この振り返りから得た教訓

**パラメータのチューニングは、入力の悪さを隠す作業になりやすい。**

今日いじった数値のほとんどは、
「サーボ音が混ざる」「マイクが遠い」「音量が変わる」を補正するためのものだった。
**入力を変えれば、そのパラメータ自体が消える。**

チューニングを始める前に一度問う ──
**「この値は何を補正しているのか。その原因は直せないのか。」**
