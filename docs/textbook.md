# 1章　まず、出荷時のまま遊ぶ

## 1-1. 何を買うか

**M5Stack 公式キット K151 / K151-R** 一択でよい。

| 項目 | 中身 |
|---|---|
| コントローラ | M5Stack CoreS3（ESP32-S3） |
| サーボ | フィードバック付き2基（横360°連続回転／縦90°） |
| カメラ | GC0308 / 0.3MP |
| マイク | デュアル |
| センサ | 近接・環境光、9軸IMU、**3ゾーン容量タッチ（Si12T）** |
| その他 | **12個の RGB LED**、NFC、赤外線、Grove ×3 |
| バッテリー | 550mAh |

## 1-2. USBポートは2つある。役割が違う

**ここで最初につまずく人が多い。**

| 位置 | 用途 |
|---|---|
| CoreS3 本体側 | **書き込み・シリアル。** PC と繋ぐのはこちら |
| ベース側 | 給電のみ |

書き込みができないときは、**まず挿している穴を疑う。**

## 1-3. 出荷時ファームで動かす

**いきなり自前構成にしない。** 先に「本来どう動くのか」を体で知っておく。
あとで自作と比べる基準になる。

初期設定は本体の Wi-Fi 設定 UI から。詳細は [setup-day1.md](setup-day1.md)。

### ここで測っておくこと（後で必ず効く）

- **応答の速さ**（自前構成にすると必ず遅くなる。どれだけ許せるかの基準）
- 騒がしい場所でウェイクワードが通るか
- **放置したときの挙動**

> 実測：放置すると**キョロキョロ見回す**。これは想像以上に不気味だった。
> 卓の上で無人のロボットが見回していると、それだけで印象が悪くなる。
> **待機は動かさないほうがいい**、と決める根拠になった。

# 2章　戻れるようにする（★飛ばさない）

## 2-1. バックアップを取る

```bash
esptool --port /dev/cu.usbmodem* read_flash 0 0x1000000 backup/factory.bin
```

**焼く前に必ず取る。** 出荷時ファームは配布されていないので、
取り忘れると**二度と出荷時の状態に戻せない。**

## 2-2. アンバインドする

**焼く前に、スマホアプリ側から必ずアンバインドする。**

忘れると、クラウド側には「この個体は誰々のもの」という記録が残ったまま、
実機だけ別物になる。**ペアリングの不整合が起き、あとから解消しにくい。**

## 2-3. 覚悟しておくこと

**一度、喋らなくなる。**

自前構成に切り替えると、会話は自分で組み直すまで戻らない。
**それが嫌なら、ここで止めて出荷時のまま使うのが正解。**

# 3章　母艦に gateway を立てる

## 3-1. gateway とは何か

実機は AI ではない。**入力を送り、指示を受けて体を動かすだけの I/O ゲートウェイ**。
その相手をするのが gateway。

```
  マイク・カメラ・タッチ  ──▶  スタックチャン  ──▶  gateway  ──▶  頭脳
  サーボ・LED・画面      ◀──   （ESP32-S3）   ◀──  （母艦）  ◀──
```

ここでは **stackchan-mcp**（kisaragi-mochi 氏 / MIT）を使う。
Python だけで動くので、**Apple Silicon で詰まらない。**

## 3-2. 立てる

```bash
git clone <stackchan-mcp> vendor/stackchan-mcp
./scripts/setup.sh          # venv と依存
./scripts/gateway.sh        # 出しっぱなしにする
```

起動すると3つの入口が開く。

```
 ESP32 の接続先 : ws://<LAN IP>:8775/
 MCP            : http://127.0.0.1:8767/mcp
 写真の受け口   : http://<LAN IP>:8776/
```

### 罠：LAN IP は「列挙順」で取らない

有線と Wi-Fi が同じサブネットに居ると、**日によって拾う IP が変わる。**

```bash
DEV=$(route -n get default | awk '/interface:/{print $2}')
ipconfig getifaddr "$DEV"
```

**既定経路のインターフェースから取る。** 抜き差しで死なない方を選ぶ。

# 4章　ファームを焼く（★ここが一番詰まる）

## 4-1. どのファームにするか

| 選択肢 | 判断 |
|---|---|
| 出荷時 | 速いが**従わない**。接続先も会話も向こうの都合 |
| 元祖 stack-chan | 素直だが機能は自分で足す |
| **xiaozhi 系 + stackchan-mcp** | **これを選んだ。**MCP で道具として呼べる |

決め手は**制御できること**。出荷時は速いが、こちらの指示で動かせない。

## 4-2. 焼く

```bash
esptool --port /dev/cu.usbmodem* write_flash 0 firmware/merged-binary.bin
```

## 4-3. 関門①　画面に6桁の数字が出て先へ進まない

**症状：** 起動すると `062047` のような6桁が表示され、
「未登録だ」と返され続ける。**成功するまで無限ループする。**

**原因：** xiaozhi 系ファームは起動時に `ota_url` へ問い合わせる。
そこで `activation` セクションを返されると、登録が済むまで進まない。

**対処：** `ota_url` をローカルの小さなスタブに向ける。

```python
# activation を入れない = アクティベーション不要
# firmware.version を現在と同じにする = 新しい版は無い
{"firmware": {"version": "1.16.0", "url": ""}}
```

`scripts/ota_stub.py` がそれ。**サーバを立てるのではなく、返事を変えるだけ。**

## 4-4. 関門②　焼き直したのに古い接続先へ行く

**症状：** ファームを入れ替えたのに、実機が `wss://api.tenclass.net/...` へ行き続ける。

**原因：** **NVS はファームを焼いても消えない。**
出荷時ファームが書いた `websocket.url` が生き残っている。

**対処：** NVS 領域だけ消す。**バックアップを取ってから。**

```bash
esptool --port /dev/cu.usbmodem* erase-region 0x9000 0x6000
```

> **教訓：永続領域は焼いても消えない。**
> 「焼き直したのに直らない」ときは、まず消えない場所を疑う。

## 4-5. 接続には2段の関門がある

```
  ① OTA 問い合わせ（ota_url）      ← 6桁コードはここ
  ② WebSocket 接続（websocket.url）← NVS の残留はここ
```

**両方通らないと繋がらない。** 片方だけ直しても症状は変わらない。

## 4-6. 接続先を空にすると mDNS で探す

`websocket.url` を**空にする**と、実機は `_stackchan-mcp._tcp.local.` を探す。
**同じ LAN に居る gateway を自動で見つける。**

これが効くのは、母艦を持ち替えるとき。

| | 自宅 | 会場 |
|---|---|---|
| gateway | 据え置きの Mac | 持ち出す Mac |

**本体に触らずに切り替わる。** 現場で Wi-Fi 設定 UI を開く羽目にならない。

# 5章　自分のコードで体を動かす

## 5-1. 繋がったか確かめる

```bash
./.venv/bin/python scripts/status.py
```

`tools=40` が見えれば実機の道具が全部見えている。

## 5-2. MCP は「道具の並べ方」を決めた規格

覚える動詞は3つだけ。

```
  initialize   挨拶する
  tools/list   何ができるか訊く
  tools/call   呼ぶ
```

実機の機能（首・LED・カメラ・タッチ）が、**そのまま道具として並ぶ。**

> **MCP は取扱説明書と製品を同一物にした。**
> 「何ができるか」を実機に訊けるので、**古い設計文書を読んで嘘を掴まない。**

## 5-3. 首の角度で必ず一度は間違える

**pitch は「中心45度からの差」で送る。**

```
  servo_pitch = 45（中心）+ 送った値
```

45 を送ると 90 になり、上限で丸められて**真下を向いたまま固まる。**

> 実際にこれで1時間溶かした。**ソースを読んでも気づけない。**
> 送っている値を実測するまで分からなかった。

**可動範囲**：yaw ±90° / pitch は中心から ±40°。
**超えた分は黙って丸められる。** エラーは返らない。

## 5-4. 「動いた」は目視で判断しない

```bash
./.venv/bin/python app/dj/console.py --verify
```

10秒ぶん実際に送った角度を測り、可動範囲と「真下を向いていないか」を判定する。

> **ログに出ない挙動は、動いていないのと同じ。**

# 6章　表情を自作する

## 6-1. 出荷時の顔は入っていない

ファームに同梱の `avatar_images.cc` は **1×1 の黒い点のプレースホルダ**。
**顔の絵は自分で入れる。**

## 6-2. 元の絵からそのまま持ってくる

近似で描くと「小さなスタンプ」みたいになって、**別物になる。**
本家 m5stack-avatar（meganetaaan 氏 / MIT）の**描画コードを移植する**のが正解。

```
  表情6  idle / happy / thinking / sad / surprised / embarrassed
  目3    open / half / closed
  口5    closed / half / open / e / u
  ────────────────────────────────
  14枚 → RGB565 で固めて 537,600 バイト
```

## 6-3. 色を減らすときの罠

パレットへ寄せるとき、**単純に「一番近い色」を選ぶと頬の赤みが顔全体に滲む。**
灰色が赤に吸われるため。

**赤みで先に振り分け、そのあと明度で決める。**

## 6-4. 表情は電源で消える

転送先は **PSRAM**。**電源を切ると既定の顔に戻る。**

だから**起動のたびに読み込む**のが正しい運用。3秒で終わる。

恒久的にしたいなら、ファームに焼き込む道もある
（`avatar_images.local.cc` を生成してビルド）。
ただし**表情を変えるたびに20〜30分**かかるので、**絵が固まってから。**

# 7章　音楽に合わせて踊らせる

## 7-1. 音はどこから取るか

**実機のマイクで拾う。** ケーブルは繋がない。
拾った音は Opus で母艦へ送られ、母艦側でテンポを推定する。

## 7-2. 最大の罠：自分のサーボ音で踊り続ける

**症状：** 曲を止めたのに踊り続ける。

**原因：** サーボ音は音楽の**13倍**（実測 0.16 対 0.006）。
しかも首が拍に合わせて動くので、**サーボ音が理想的な「拍」として検出される。**

**対処：** 周期的に**首を止めて、止まっている間だけ測る。**

> ここで UX の判断が要る。**止まっている姿を「測定」に見せない。**
> 4種類のキメのポーズを順番に回し、たまに頷いてから踊りに戻す。
> **毎回同じ止まり方だと「測っている」のがバレる。**

## 7-3. 閾値は必ず2つ持つ

始める閾値と止める閾値を同じにすると、**境目で点滅する。**
止める側を 0.7 倍にする。

> この日、**同じ形の対処を3回**入れることになった。
> 「オン/オフが震える」ときは、**ほぼ必ずヒステリシスの不足。**

## 7-4. 音量の見当を実測で持つ

| | 実測値 |
|---|---|
| 静か | 0.001 前後 |
| **普通の音量の音楽** | **0.005 〜 0.010** |
| サーボ音（自分） | 0.16 |

最初「全開」を 0.026 に置いていたため、**首振りが 0.9 度しか出ていなかった。**
**数字を決める前に測る。**

## 7-5. 客は左右にいる

真上にも真下にも人はいない。**横を大きく使い、縦は控えめに。**
振り付けは複数用意し、**長さも一定にしない。**

> 一定の往復を繰り返すと、どれだけ滑らかでも機械に見える。

## 7-6. 「うんうん」は sin では作れない

ゆっくり下がると頷きに見えない。
**拍の頭でガッと落として、拍の25%で戻す三角波**にする。

# 8章　電源を入れるだけで動く状態にする

## 8-1. 手順を消す

手順を分かりやすく書くより、**手順を無くすほうが効く。**

```bash
./scripts/service.sh install     # 一度だけ
```

母艦にログインすれば gateway と console が自動で上がる。
**普段やることは「実機の電源を入れる」だけ。**

## 8-2. 実機を待たせる

常駐なら、実機が来るまで**無限に待つ**設定にする（`--wait-device 0`）。
**電源を入れた瞬間に繋がる**ので、起動の順番を気にしなくてよくなる。

## 8-3. 起動の順番には意味がある

```
  ① 実機が居るか確かめる     居ないまま進むと黙って失敗する
  ② 表情を読み込む           電源で消えるので毎回
  ③ ストリームを購読
  ④ beat mode を開始         ★首とLEDを有効にして始まる
  ⑤ モードを確定             ★④に上書きされないよう必ず最後
```

**④と⑤を逆にすると、待機モードなのに踊り出す。**

## 8-4. 落とし方も作る

`kill -9` は使わない。**片付けが1つも走らない。**
実機は踊ったまま、gateway は死んだ相手を掴んだまま残る。

```
  ① beat mode を止める   先に音を聴くのをやめる
  ② 購読を解除
  ③ 首を正面へ
  ④ 待機の顔へ
```

**片付けには制限時間をつける。** 応答しない相手を待って止まらなくなるほうが困る。

## 8-5. 実機が消えて戻ったら、自動で組み直す

実機の電源を入れ直すと、**表情は消え、beat mode は死に、購読も切れる。**
見張り役が5秒ごとに確認し、戻ったら初期化をやり直す。

**生存確認は母艦側だけで済む問い合わせを使う**（実測16ms）。
実機に問い合わせる道具を短い間隔で叩くと、**音声の取り込みを邪魔する。**

# 9章　詰まったときの切り分け

## 9-1. まず健康診断

```bash
./.venv/bin/python scripts/doctor.py          # 点検
./.venv/bin/python scripts/doctor.py --fix    # 直せるものは直す
```

## 9-2. 症状と原因の対応表

| 症状 | まず疑う |
|---|---|
| 書き込めない | **USBの穴**（本体側かベース側か） |
| 6桁の数字が出て進まない | OTA の関門。スタブに向ける |
| 焼き直したのに古い接続先へ行く | **NVS が消えていない** |
| 首が真下を向いたまま | pitch の単位（**45からの差**） |
| 首が思ったより動かない | 可動範囲で黙って丸められている |
| 曲を止めても踊り続ける | **自分のサーボ音を聴いている** |
| 踊ったり止まったりする | 閾値が1つしかない |
| 表情が既定に戻った | **電源で消えた。**入れ直す |
| 動かないのにエラーも出ない | **実機が繋がっていない** |

## 9-3. この機材で一番大事な心構え

**ツール呼び出しは、失敗してもエラーを投げない。**
「開始しました」と表示されていても、実機が居なければ中身は失敗している。
**ログを見ても成功に見える。**

> だから、**始める前に実機が居ることを確かめる。**
> そして**動いたかどうかは、送った値を測って判断する。**
