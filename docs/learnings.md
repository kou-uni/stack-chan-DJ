# ベストプラクティス（他の仕事にも効く）

## 機器のプロトコルではなく、共通規格の話し方を覚える

**2026-09-08、スタックチャンを1行も理解しないまま制御できた。**

DDJ-FLX2 のつまみでロボットの首を動かすコードを書いたが、
**スタックチャン固有のプロトコルは一度も読んでいない。**
覚えたのは MCP（Model Context Protocol）クライアントの書き方だけで、
それは Anthropic が公開している**機器と無関係な汎用規格**だった。

### 層で見ると

```
自分のアプリ          ← ここだけ書く
   ↓ MCP（汎用規格）    ← ここを覚える。他の機器でも同じ
ゲートウェイ           ← 他人の成果物。機器固有の翻訳を担う
   ↓ 機器固有プロトコル  ← 読まなくてよかった
機器
```

### 何が起きたか

順序が逆に見えるが、こうなっている。

1. MCP という共通規格が**先にある**
2. ゲートウェイの作者が「うちの機器も MCP を喋れるようにしよう」と実装した
3. だから**MCP の話し方を1つ知っていれば、機器固有の言葉を覚えずに叩ける**

### だから何が変わるか

**ハードウェアを触るコストが、規格を1つ覚えるコストに置き換わった。**
次に別のロボットや機器をやるとき、それが MCP を喋るなら、
学び直すのは「その機器がどんなツールを持っているか」だけで、
通信の仕組みは丸ごと使い回せる。

`ls` でツール一覧を見て、`set_avatar` `move_head` `beat_mode_start` と読めた時点で、
**もう書ける状態になっていた。**

### 前提条件を忘れない

これが成立したのは、**ゲートウェイが公開されていたから**。
作ったのは M5Stack ではなく **kisaragi-mochi さんという個人**で、
メーカーが用意した「デフォルト」はむしろ海外クラウドに繋ぐ道の方だった。
共通規格は、**誰かがその機器のために実装してくれて初めて効く。**

## 説明書と実装を同じ場所に置くと、ズレようがなくなる

**2026-09-08、同じリポジトリの中で、両方の証拠が同時に出た。**

| | 結果 |
|---|---|
| 人が書いた設計文書（`architecture.md`） | 「音声は未実装」← **古くて嘘になっていた。計画を1つ間違えた** |
| 機械が返す道具一覧（`tools/list`） | **常に正しかった** |

なぜこうなるか。**説明と実装が別のファイルにあると必ずズレる。**
MCP のツール定義は、説明文と呼び口が**同じ1個のオブジェクト**で、
しかも**起動のたびに実物から取り直す**。構造的にズレようがない。

「AI向けの取扱説明書」ではなく、**取扱説明書と製品が同一物になった**、が正確。

### 自分で MCP サーバーを公開するときに効くこと

- **説明文が API の一部になる。** 型を書くだけでは足りず「いつ使うか」を書く
  （実例：`speed` の説明が「`high` は驚きや二度見に」まで書いていた）
- **説明文が雑だと AI が誤用する。** バグが「説明文が悪い」という形で現れる
- **取り返しのつかない動詞に注意。** AIは一覧を見て自分で選ぶので、
  `delete_all` があれば選ばれ得る

## 「動くこと」の確認と「繋がること」の確認を分ける

他人のゲートウェイを使うとき、**そのソフト自体が動くかは作者がテストしている**。
自分が確かめるべきは **自分のコードとの接続**の方。

- ツール名は合っているか
- 引数の形は合っているか
- ストリームの形式は受理されるか

実機が無くても、**ゲートウェイが自分のサーバーに接続しにきたか**で判定できた。
それが出た時点で「配管は正しい」が確定し、
残る不確実性が「書き込みが成功するか」だけに絞れた。

**取り返しのつかない操作（書き込み）の前に、取り返しのつく確認を全部終わらせる。**


## 判断を1箇所に集める

2台が「相手が居るか」を見て譲り合うと、**誰も名乗らない事故**が起きる。
MacBook は空気を読まず無条件で名乗り、Mac Studio だけが読む。
分散した合意より、**片側だけが判断する非対称な設計**の方が壊れにくい。

## 周期的な事象は、イベントではなく状態として送る

BPM128 の1拍は 469ms。ネットワーク往復がそれを丸ごと食うので、
拍を1つずつ送る方式は原理的に成立しない。
**テンポと位相だけ送り、刻むのは端末側。** 更新は数秒に1回でいい。
回線が揺れても崩れない。

## 確実性が要るものは自分で書き、曖昧な自然文だけLLMに投げる

全部LLMに任せると、朝の予定読み上げが気まぐれで失敗する。
**「LLMに何を任せるか」ではなく「失敗が許されないものを先に手で書き切る」**という順番。

## 新しい変数は、他が固定されたときに1つだけ入れる

テザリングで開発し続けると、毎回のデバッグに「回線のせいかも」が混ざる。
最後に回すと「できないやん」になる。
**節目で1回ずつ、小さいスコープで入れる。**

## 軽い方から積んで、手応えを先に取る

制御は Python だけで動く。会話はサーバー構築で重い。
順番を逆にすると、最初の成功体験までが遠くなって続かない。

## 戻せる状態を先に作ってから壊す

バックアップと復元手順が手元にあると、実験の心理的コストが劇的に下がる。
**「気軽に載せ替えてよい」と言えるかどうか**が、試行回数を決める。

## 環境ごとにコードを分けない。設定だけ変える

「MacBook用」「MacStudio用」に分けた瞬間、
**片方でしか直していないバグ**が生まれる。そして本番で踏む。

## 未知の要素を2つ同時に入れない（切り分けの順番）

mDNS 自動検出を最初から狙うと、失敗したとき
「NVSに古いURLが残っていたのか」「mDNSが効かないのか」が区別できない。

**まず明示URLで確実に繋ぐ → 繋がってから mDNS に切り替える。**
片方ずつ動かせば、失敗は必ず片方に帰属する。

## 一次資料は1つ。分割コピーを作らない

要約を別ファイルに切ると、必ず内容がずれる。
索引と差分メモは作ってよいが、**本文の複製は作らない**。

# アンチパターン

## 両方に判断させる

**なぜそうしたくなるか**：対称な設計の方が美しく見える。
**何が起きるか**：相互に譲り合って誰も名乗らない。あるいは同時に名乗ってレースになる。

## 全部をLLMに任せる

**なぜ**：エージェントらしくて格好いい。
**何が**：決定論的であるべき処理が確率的になる。定時通知が気まぐれで失敗する。

## 拍を1つずつネットワークで送る

**なぜ**：素直な実装に見える。
**何が**：往復が1拍を超えると同期不能。**遅いのではなく、原理的に無理**。

## 実機にロジックを載せる

**なぜ**：自己完結して見える。
**何が**：修正のたびに書き込み直し。1回の試行が数分になり、試行回数が落ちる。
**例外**：低遅延が要件になった瞬間、判断は反転する（ダンスの位相生成）。

## 理由のないアイドルモーション

**なぜ**：「そこにいる感」を出したくなる。
**何が**：**動く理由が観測者に見えないと、生き物らしさではなく不気味さになる。**
実測でキョロキョロが本当に気持ち悪かった。待機は動かさない方がいい。

## ヒステリシスなしのフェイルオーバー

**なぜ**：素早く切り替わる方が良いと思える。
**何が**：スリープや瞬断で名乗ったり取り下げたりバタつく。**中途半端な故障が一番厄介**。

## 連続追従をMCPツール経由でやる

**なぜ**：既にツールがあるので使いたくなる。
**何が**：1回1回の呼び出し向けの層にオーバーヘッドが乗り、追従が遅れる。
**正解**：下の層（WebSocket）を直接叩く。

## サーボを全拍で振る

**なぜ**：拍に全部当てた方が同期して見える気がする。
**何が**：BPM128 で往復4.3回/秒。発熱と摩耗。
**しかも** 2拍に1回の方が**人間の頭の振り方に近くて自然に見える**。

## リポジトリの設計文書を読んで、計画を立てた気になる

**なぜそうしたくなるか**：`architecture.md` にロードマップが書いてあると、それが現状に見える。
**何が起きるか**：**2026-09-08、これで計画を丸ごと1つ間違えた。**
`architecture.md` の「Phase 5 = 音声は未実装」を信じて、
会話用に別サーバー（xiaozhi-esp32-server）を立てる計画を立てていた。
実際には `stt/` `tts/` `beat/` が既に実装済みで、必要なかった。

**正解**：**設計文書ではなく、ディレクトリ一覧と CHANGELOG を先に見る。**
`ls` と `CHANGELOG` は嘘をつかない。設計文書は書かれた時点で止まる。
依存先の状態を確かめるときは、散文より構造を見る。

## 「LAN IP」を1つだと思い込む

**なぜそうしたくなるか**：`ipconfig getifaddr en0` のような1行で取れる気がする。
**何が起きるか**：**2026-09-08、この Mac Studio は en0 を使っていなかった。**
実際は **有線(en7)=192.168.0.123 と Wi-Fi(en1)=192.168.0.179 の両方が同じサブネットに居た。**
インターフェースの列挙順で拾うと、**日によって違うIPが出る**。
そのIPをファームに焼くので、**ケーブルを抜いた瞬間に実機が繋がらなくなる**。

**正解**：**既定経路のインターフェースから取る。**

```bash
DEV=$(route -n get default | awk '/interface:/{print $2}')
ipconfig getifaddr "$DEV"
```

そもそも IP を焼かずに済むなら、それが最善（mDNS）。

## 依存サービスのポートが空いている前提で書く

**なぜ**：既定ポートは自分のものだと感じる。
**何が**：8765 は**別プロジェクト（obsidian_rsi）が3日前から掴んでいた**。
gateway が起動時に `address already in use` で落ちた。
**他人のプロセスを止めて解決しない。** 自分のポートをずらす（8775 にした）。
そしてそのポート番号は、**ファームに焼く接続先URLにも波及する**。

## LEDの「最大電流」を計算せずに繋ぐ

**なぜそうしたくなるか**：コネクタが刺さる＝使える、と感じる。
Grove ケーブルが同梱されていると、なおさら「対応済み」に見える。
**何が起きるか**：**A093（0.5m/30LED）は全開で 5V@1.8A。**
CoreS3 の Grove ポートからは取れない。全部を白で全開にすると電圧が落ち、
**本体ごと再起動する**。しかも本番で「一番派手にした瞬間」に落ちる。

**正解**：**LED は個数 × 60mA で最大電流を先に出す。**
そのうえで**ソフト側に明るさ上限を持たせる**（既定 0.35 にした）。
色付き3割なら 200〜400mA に収まる。
仕様表の `18 W/メートル` のような行を、繋ぐ前に1回読む。

## 低解像度では「形の微差」より「独立した記号」

本家 m5stack-avatar は、目の削り方だけで6つの表情を作り分けている。
Angry は上部を三角に、Sad は逆向きの三角に、Doubt は長方形に削る。

**160×120 に縮小すると、この差は全部消えた。**
削る量が目の高さの1/4しかなく、35pxの目では8pxしか変わらない。
そこにファーム側の拡大補間で1〜2pxの滲みが乗って、3つとも同じ顔になった。

**同じライブラリの `Effect.h` に答えがあった。**
表情とは別に、♥ / 汗 / 井桁 / 落ち込み線 を画面の隅に描くレイヤー。
**独立した図形は絶対に見落とさない。**

一般化すると、**表示が小さい・粗い・遠いほど、
「形を変える」より「記号を足す」方が伝わる。**
アイコンにバッジを付ける、状態を色ではなく形で示す、なども同じ理屈。

## 「動かない、でも生きている」の境界線

待機中に首を動かすと不気味になる（出荷時ファームで実測）。
かといって完全に静止すると、電源が切れているように見える。

**まばたきだけがその境界線だった。**
首は動かさない。目だけが3〜6秒おきに閉じる。それで「生きている」が成立する。

存在感は動きの量ではなく、**動く理由が読めるかどうか**で決まる。
まばたきは理由を問われない数少ない動き。

## モードは1つの軸だけを表す

最初 待機／DJ／手動 の3モードを作った。**待機と手動の区別が実質なかった。**
つまみも表情もどのモードでも効くので、違いは「音に反応するか」だけだった。

**2つに減らした。OFF（音に反応しない）／DJ（音に反応する）。**

モードを増やすほど「これは何が違うんだっけ」になる。
**1モード＝1つの軸**にすると、名前を見ただけで挙動が分かる。

**そして、モードで無効にしていいものを間違えない。**
つまみ・表情パッド・うなずき・頭なでは**常に効く**ようにした。
人が今まさに操作しているものを、こちらの都合で無効にしてはいけない。

## トグルにしていい操作と、片方向だけの操作がある

PLAYボタンで DJモードに入るようにした。**トグルにはしなかった。**
DJはセット中に何度もPLAYを押す。押すたびに切り替わったら使えない。

**PLAYはONだけ。OFFは別の経路（モードパッド／曲が来ない時間での自動復帰）。**

一般化すると、**その操作が繰り返されるものかどうかで、トグルの可否が決まる。**
「1回しか押さない」ならトグルでよい。「何度も押す」なら片方向にして、
逆方向は別の入口を用意する。

## 操作していることを、相手に返す

つまみを回している間だけ表情を変えるようにした。

操作している側は**自分の入力が届いているか分からない**。
首が動いても、自分が動かしたのか勝手に動いたのか区別がつかない。
**顔が変われば、届いたことが確実に分かる。**

戻すタイミングは**主導権を手放すのと同じ瞬間**に揃えた。
顔が先に戻ると「もう効いていない」ように見え、後だと間延びする。
**1つの出来事は、1つの瞬間に見せる。**

## 意図せず起きる操作に、状態を変える意味を持たせない

音（拍の規則性）だけで「曲が鳴っているか」を判定すると、
**話し声も拍手も食器の音も「曲」に見える。** 閾値をどう調整しても外れるし、
外れたときに会場で直せない。

→ **推測をやめて、人が明示的に切り替える**方向に倒した。ここまでは良い。

そこで最初、**頭を撫でたらモードが変わる**ようにした。**これは間違いだった。**

**可愛いから触る人がいる。** 参加者は機能を呼び出す気などなく、ただ撫でている。
そこに状態変更を割り当てると、**触った人の意図と、起きたことがずれる。**

**同じ「押す・触る」でも、誰がどんな意図でやるかで、割り当てていいものが変わる。**

| 操作 | 意図 | 割り当ててよいもの |
|---|---|---|
| 頭を撫でる | つい触ってしまう | **反応**（照れる・喜ぶ）。状態は変えない |
| DJ卓のパッドを押す | 明確に操作している | **状態変更**（モード切替） |
| PLAYを押す | 「これから音を出す」と既に宣言している | **状態変更**。推測より確実 |

最後の行が効く。**利用者が既に別の理由で行っている操作から、意図を読み取れる。**
新しいジェスチャを覚えさせるより、**既にある動作に乗る**方が学習コストがゼロになる。

## 会場の前提（2026-09-08 本人談）

**Crypto Cafe and Bar は広くない。DJもそこまで大音量にしない。**

開発中に「これくらい鳴っていれば」と思った音量（RMS 0.02）は、
本人いわく **かなり大きい方**。当日の想定は **0.005〜0.009**。

満点の基準（`--full-level`）は **0.005** に置いた。
**当日は `scripts/hear.py` で実測してから決め直すこと。**

## 基準は理想値ではなく、実際に来る値に置く

音量からノリの強さを出すとき、**「しっかり鳴っている曲＝0.026」を満点にした。**
実際のDJの音量は **0.005〜0.010** だった。3分の1しかない。

結果、振り幅が **0.9°〜1.3°** にしかならず、**「動いていない」ようにしか見えなかった。**
壊れていないのに壊れて見える、いちばん厄介な形。

**症状は「動かない」としてしか現れない。** 計算は正しく、閾値も超えていて、
コマンドも届いている。**基準の置き場所だけが間違っていた。**

**正解**：一度でも実測したなら、**その値を基準にする。**
「本来これくらいのはず」で組まない。
実測が理想と桁違いなら、理想の方を捨てる。

## 開始と停止の閾値を同じにしない（ヒステリシス）

音量 0.006 を境に「踊る／止まる」を判定した。
実際の音量が 0.0087 で境界の近くを漂ったので、
**数秒おきに「踊りだした／曲が終わった」を往復した。**

止める閾値を**始める閾値の0.7倍**にしたら収まった。

**境界をまたぐ判定は、必ず往復する。** 入りと出で別の線を引く。
これは今日3回目のヒステリシス（モードの名乗り、タッチの固着、そしてこれ）。
**閾値を1本だけ引いたら、そこが振動点になると思ってよい。**

## 滑らかな単調は、粗い変化より機械に見える

首の動きを sin の往復にして「滑らかになった」と思っていた。
**本人の評価は「動きがとても一定すぎる」。**

滑らかさを上げても、**同じ動きを永久に繰り返す限り機械にしか見えない。**
生き物らしさは滑らかさではなく**変化**から来る。

人は8拍くらいで動きを変え、1拍目にアクセントを置き、ときどき溜める。
**6種類のフレーズを8拍ごとに切り替える**だけで、印象が変わった。

**「もっと自然に」を滑らかさの問題だと読み違えない。**
たいていは変化の問題。

## 停止を隠さず、振り付けにする

自分のサーボ音で耳が塞がるので、測るには止まるしかない。
最初その1.5秒を**隠そうとしていた**。

正解は**振り付けの一部にすること**。しかも**1種類だと見破られる**ので、
見上げる／首をかしげる／うつむいて溜める／逆に振ってキメる、の4種を回す。
それぞれに顔とLEDを付ける。

**制約から生まれた動作ほど、意味づけると強い。**
本当に「音楽を聴くために止まっている」ので、演出が嘘をついていない。

## 「余計な反応」をバグと決めつけない

話し声に反応して踊るのを、私は**バグとして消そうとしていた。**
デジタル入力に切り替えれば消える、と提案までした。

**本人の指摘で反転した。**
「喋っている最中に踊るような可愛い仕草も、この状態だとついてくる」

ロボットにとって、**予定外の反応は必ずしも欠陥ではない。**
「大きな音がしたら反応する」は、生き物としてむしろ正しい。
純度を上げて消すと、可愛さも一緒に消える。

**正しい扱いは「消す」ではなく「強さを変える」だった。**

| 音 | 反応 |
|---|---|
| 曲（大きい＋拍が明確） | 全力で踊る |
| 話し声（小さい＋拍が曖昧） | **軽くうなずく**。会話の邪魔をしない |
| 無音 | 止まる |

判定を**2値から連続量に変えた**だけで、問題が機能に変わった。

**閾値で切るのは、情報を捨てる行為。** 手元には `level` と `confidence` という
連続量が最初からあった。それを 0/1 に潰していたから、
「踊るか踊らないか」という不毛な二択になっていた。

## 動き出しと止まりに、助走をつける

拍を検出した瞬間にフルスイングで振り始めていた。**機械的に見える。**

人は曲が始まって数拍聴いてから乗り出す。
**立ち上がりを2秒、立ち下がりを1.2秒**にしたら、生き物らしくなった。
非対称なのも意図的で、**乗るのはゆっくり、やめるのは少し速い。**

止めるときも急停止させない。**振り幅が細くなって消える。**

一般化すると、**状態の変化そのものが表現になる。**
「AからBへ変わる」を瞬時に済ませると、機械に見える。

## 隠せない制約は、演出にしてしまう

サーボ音で自分の耳が塞がるので、**踊りながら外の音を聞けない**。
6秒ごとに1.5秒だけ首を止めて測る、という解決になった。

その1.5秒を**隠そうとすると「引っかかり」に見える。**
そこで顔を `embarrassed`（♥と頬の赤）にし、LEDを桃色のゆっくりした明滅に変えた。
**「曲に聴き入って、思わず動きが止まった」に見える。**

強いのは、**演出が嘘をついていないこと**。
本当に「音楽を聴くために止まっている」ので、見た目と実装が一致している。
取ってつけたアニメーションではなく、**動作の意味そのものを見せている**。

**制約を隠すか、意味づけるか。** 隠せない長さのものは、意味づけた方が勝つ。

## ロボットは自分の音を聞く（センサーとアクチュエータが同じ体に載っている）

**2026-09-08、今日いちばんの発見。**

音楽に合わせて首を振らせたら、**曲を止めても踊り続けた。**
原因を測ったら、決定的な数字が出た。

| | マイクが拾う音量 |
|---|---|
| 首が動いている | 0.039 〜 **0.164** |
| 首を止めた | **0.0035 〜 0.0043** |

**40倍。しかも音楽そのもの（0.06）より、サーボの音の方が大きい。**

さらに悪いことに、**首は拍に同期して動く**。だからサーボ音は
「規則正しい拍」として検出され、それを聞いてまた踊る。
**完全な自己増幅ループ**になっていた。

### 音量では切り分けられない

「静かになったら止める」を実装するのに音量を使ったが、
**自分が出す音の方が大きいので、閾値をどこに置いても分離できない。**

### 解決：踊りながら、ときどき耳を澄ます

**6秒ごとに首を0.9秒だけ止めて測る。** サーボ音が消えて初めて、
外の世界が鳴っているかが分かる。LEDは止めない（音を出さないので）。
見た目は「踊りの中の一瞬の溜め」になり、演出としても成立する。

### 一般化

**センサーとアクチュエータが同じ筐体にあると、必ず自己観測が混ざる。**
カメラを載せた雲台、マイクを積んだドローン、加速度計を持つ振動体、
みんな同じ問題を持つ。

対策は3つしかない。**物理的に離す／自分の出力を差し引く／動きを止めて測る。**
今回は3つ目を選んだ。一番安く、一番確実だった。

## 監視するために送るコマンドが、監視対象を壊す

**2026-09-08、音楽で踊らせるのに半日溶かした最大の原因。**

「音が止まったら踊りを畳む」監督を書いた。0.4秒ごとに状態を見て、
変化のたびに5つのコマンド（更新・LED消灯・首を正面・表情・まばたき）を送った。

**その結果、拍の検出そのものが壊れた。**
音声と制御が同じ WebSocket を通るので、コマンドが音声フレームを押しのけていた。
症状は「BPMは126で安定しているのに、拍が数秒おきに途切れる」という奇妙な形で出た。

しかも自分の監督が2秒おきに「踊りだした／止まった」を往復していたので、
**壊れるほどコマンドが増え、増えるほど壊れる**という正のフィードバックになっていた。

**正解**：観測の間隔を広げ（0.4秒→1.0秒）、送るコマンドを減らす。
瞬間ごとの判断は相手（gateway）が自分でやっている。
**二重に判定しない。自分の仕事は「本当に終わったとき」だけに絞る。**

**一般化**：監視は無料ではない。ポーリングの頻度と、そこから出るコマンドの量は、
対象の性能を削る。**測るために壊す**のは、分散システムでもプロファイラでも起きる。

## 「緩くする」場所を間違える

「もう少し緩く」と言われて、**自分の判定を緩めた。効かなかった。**

実際に止めていたのは gateway 側の `MIN_MOTION_CONFIDENCE = 0.35` で、
そこに届かない限り首は動かない。自分の側でいくら「踊っている」と判定しても、
**相手が振らないと決めていたら何も起きない。**

**正解**：**実際に効いている門番を先に特定する。**
自分の条件は、相手の条件より緩くても厳しくても意味がない。
ログが「踊りだしました」と出ながら首が動かないなら、判定の主体が別にある。

## 感度は上げれば良いものではない（音量と逆に動かす）

拍の検出は「直近の平均の1.65倍に跳ねた瞬間」を探す。
感度はその**下限**を決める（0.2→高い下限、0.9→低い下限）。

音量が足りないとき、反射的に感度を上げた。**悪化した。**
下限が下がると、ハイハットや残響まで拾って**拍の間隔がバラバラになる**。
不応期は0.24秒（毎秒4.2回が上限）なので、それを超える検出はBPMを揺らすだけ。

実測した掃引（音量が十分なとき）:

| 感度 | 確信度 | BPMのブレ |
|---|---|---|
| **0.2** | **0.84** | **±0.0** |
| 0.5 | 0.69 | ±0.1 |
| 0.9 | 0.79 | ±0.1 |

**音が大きいほど感度は下げる。** 逆に動かす。

## 平均を測って「足りている」と判断する

音量を測るツールを書き、RMS（平均）で「既定の感度で拾える。狙い目」と判定させた。
**その判定が間違っていた。** 音量は足りていたが、拍は立っていなかった。

拍の検出が見ているのは平均ではなく**平均からの突出**。
なだらかに上下する音は、いくら大きくても拍にならない。

**正解**：**判定に使う指標を、相手の判定式から逆算して決める。**
ツールに「平均の1.65倍を超える山が毎秒何回あるか」を足したら、
初めて現実と一致した（1.2回/秒が下限）。

## 状態を戻す条件を、片方の経路にしか書かない

**なぜそうしたくなるか**：「脱力したら、次に首を動かすときに戻せばいい」は自然に見える。
**何が起きるか**：**2026-09-08、dry-run のログで見つけた。**
トルク復帰を「つまみを回したとき」にだけ書いていたので、
**つまみを触らずに次の表情へ行くと、脱力したまま**になった。
本番なら「なぜか首が動かない」として現れ、原因を探す羽目になる。

**正解**：**状態を変える出口を全部数える。**
入口が1つでも、出口は複数ある。
「この状態から抜ける経路は他にないか」を、実装した直後に1回問う。

## 図のズレは、目で追わず不変条件として検査する

図解を作ったら本人から「全体的にずれている」と指摘された。
目視で追う代わりに**検査を3つ書いた**ら、自分では気づけないものまで出た。

| 検査 | 見つけたもの |
|---|---|
| 線やパスの端点が、箱の内側に入っていないか | 線が箱の中から生えていた |
| 日本語テキストの実幅が箱から溢れないか（全角1.0em / 半角0.55em） | なし |
| **アニメーションの経路が、描いた線と一致しているか** | **パケットが線と逆向きに流れていた** |

3つ目が効いた。**向きが逆＝意味が逆**なのに、静止画では絶対に気づけない。
「gateway が購読しに来る」と説明しながら、粒は反対向きに動いていた。

**図も検査できる。** 座標は数値なので、「端点は箱の縁にあるはず」
「アニメの経路は線と同じはず」という不変条件を書ける。
レイアウト崩れをスクリーンショットの目視で潰すのは、最後の手段。

## 受理されなかったフレームは、黙って捨てられる

LEDが光らない。接続は成功し、受信数も増えている。だが実機には届いていない。
`status` を見たら答えが書いてあった。

    frames_received = 728   frames_sent = 0   frames_dropped = 728

**728フレーム全部が捨てられていた。エラーは一度も返ってこない。**

原因は**フィールド名の違い**。同じゲートウェイの2つのストリームで、形が違った。

    pose : {"frame": "continuous", "yaw":…, "pitch":…}
    LED  : {"kind":  "continuous", "ts":…, "colors":[…]}

「似ているから同じだろう」で `frame` のまま送っていた。

**教訓：ストリームを繋いだら、まず `status` で送信数を見る。**
「接続できた」は「受理されている」を意味しない。
検証に落ちたデータは、例外ではなくカウンタになって静かに積み上がる。

## ログに出ない挙動は、動いていないのと同じ

つまみの値は内部変数を更新するだけで、何も表示していなかった。
パッドは全部ログに出るのに、つまみだけ1行も出ない。
**動いているのか壊れているのか、区別がつかない状態**だった。

現在値を1行で出すようにしたら、両端まできれいに走破しているのが見えて、
**同定した CC番号と入力範囲が正しいことまで同時に裏取りできた。**
可視化はデバッグの道具であると同時に、**検証の道具**でもある。

## 部分的な観測を「実測値」として確定させる

**なぜそうしたくなるか**：実際に測った数字なので、推測より信用できる気がする。
**何が起きるか**：**2026-09-08、つまみの可動域を半分だと誤って確定した。**
本人が中央で止めた区間を全可動域と解釈し、「0〜64が全可動域」とドキュメントに書いた。
再測定したら 0〜127 で、128種すべての値が出ていた。

**正解**：**測定側から「端に達したか」は分からない。**
本人の「端までやった」という申告を確定条件にしない。
**両端の値そのものが観測されたこと**（0 と 127 の両方が出た）を条件にする。
観測が部分的なうちは「暫定」と書く。実測は推測より強いが、**不完全な実測は推測より危険**
── 数字がある分、疑われずに下流へ流れていく。

## 便利な機能を見つけて、元の要件を格下げする

**なぜそうしたくなるか**：既存機能が要件の一部を満たすと、
残りも「その延長」に見えて、まとめて解決した気になる。
**何が起きるか**：**2026-09-08、これで要件を1つ落としかけた。**
`beat_mode`（音でBPMを取って踊る）を見つけて、
「DJ連携に配線は要らない」と書いてしまった。
だが本来の要件は「**つまみを回すと首が回る／別のつまみでうなずく／ボタンで表情が変わる**」で、
**つまみの角度もボタン押下も、音からは絶対に取れない。**

**正解**：新しい手段が見つかったら、**要件表に照らして1行ずつ消し込む。**
「だいたい満たせそう」で線を引かない。指摘されて気づいた。

## 関門が1つだと思い込む（★2026-09-08 最大の詰まり）

**なぜそうしたくなるか**：接続先URLを設定したのだから、そこへ繋ぎに行くはず、と思う。
**何が起きたか**：**設定は正しく保存されていたのに、繋がらなかった。**

xiaozhi 系ファームには**2段の関門**がある。

```
① OTA問い合わせ（ota_url） → 「未登録だ」と6桁コードを返される → 成功するまで無限ループ
② WebSocket 接続（websocket.url） ← ここまで到達しない
```

NVS を見たら `websocket.url` は正しく入っていた。
**設定が効いていないのではなく、その手前で止まっていた。**

**切り分けの決め手**は本人の「Advanced 書いたけどねぇ」だった。
それで「設定は正しい／別の場所が原因」に絞れた。
**動かない＝設定が悪い、と決めつけない。**

### 抜け方

ソースを読むと、`activation` セクションを含まない JSON を返せば関門を通ることが分かった。
`ota_url` をローカルの小さなスタブに向けるだけでよい（`scripts/ota_stub.py`）。

```json
{"firmware": {"version": "<現在と同じ>", "url": ""}}
```

失敗させて抜ける道もあるが、`MAX_RETRY=10` で待ち時間が倍々（10秒→20→40…）なので数時間かかる。
**「失敗させる」より「成功させる」方が速いことがある。**

## 前のファームが残した設定を、新しいファームが消してくれると思い込む

**なぜそうしたくなるか**：焼き直したのだから初期状態だと感じる。
**何が起きるか**：**NVS は焼いても消えない。**
出荷時ファームが書いた `websocket.url=wss://api.tenclass.net/...` が残り、
「NVSが空ならデフォルトを使う」というフォールバックが発動しない。
mDNS discovery も `websocket.url` が空でないと動かないので、同時に死ぬ。
結果、新しいファームなのに**元のクラウドを呼び続ける**。

**正解**：**永続領域は焼却対象ではない**と最初から扱う。
焼く前に「前の持ち主が何を書き残したか」を確認する。

**何が**：キャプティブポータル非対応。5GHz。当日その場で直せない。

# ノウハウ（この機材・この構成の固有知識）

## ハード・初期設定

- **Wi-Fi は 2.4GHz のみ。** 5GHz非対応、キャプティブポータル非対応
- **iPhoneテザリングはデフォルト5GHz** → 設定 → インターネット共有 → 「互換性を優先」をオン
- **USBは足側に挿す。** 首が回るので頭側だとケーブルを自分で抜く
- ダウンロードモード＝底面 RST を3秒長押し、隣のLEDが緑になったら離す
- 焼く前に **StackChan World からアンバインド**。忘れるとペアリング不整合
- M5Burner で出荷時に戻せる（往復自由）。**Only Official にチェック**
- **電源が入った状態で首を手で回すと壊れる**

## ネットワーク

- Tailscale Funnel が待てるのは **HTTPS の 443 / 8443 / 10000 のみ**。**wss は通る**
- 回線が v6プラス（MAP-E）なのでポート開放は使えない。トンネル前提
- **ESP32 に Tailscale は入らない。** 公開するのは Mac 側
- iPhoneのWi-Fiテザリングは AP isolation が読めない
  → **MacBook を 2.4GHz 親APにする方が堅い**（iPhone は USB で回線だけ供給）

## ソフト

- 公式 xiaozhi-esp32-server の Docker イメージは **v0.8.2 以降 x86 のみ**。ARM64 は手動ビルド
- エンドポイント：`ws://<host>:8000/xiaozhi/v1/` ／ OTA `http://<host>:8003/xiaozhi/ota/` ／ 管理画面 `:8002`
- **ファーム同梱の `avatar_images.cc` は 1×1 の黒い点のプレースホルダ。** 顔の絵が入っていない。
  `load_avatar_set` で自前の14枚（160×120 RGB565 = 537,600バイト）を焼く必要がある
- 本家 m5stack-avatar には**絵が無く描画コードだけ**がある。移植して使う（MIT）
- **ファームは `lv_image_set_scale(512)` で2倍にするが `antialias` を切っていない。**
  → 素材をどれだけ二値化しても1〜2pxの滲みが必ず乗る。細い要素を作らないのが唯一の対策
- 14枚の内訳は **表情6＋目3＋口5**。目と口は**アニメーション用のコマ**で、
  まばたきと口パクは**実機側がローカルで回す**（ネットワークの揺れが乗らない）
- **音量の計算窓は1.2秒。** 首を止めて音を測るなら、それより長く待つ。
  0.9秒で測ったら直前のサーボ音が窓に残って 0.095 を拾い、誤判定した
- **`follow_led_stream` と `follow_pose_stream` はフレームの形が違う。**
  pose は `{"frame": …, "yaw", "pitch"}`、LEDは `{"kind": …, "ts", "colors"}`。
  間違えると**エラーなしで全部捨てられる**（`status` の `frames_dropped` で気づく）
- LED の `target` は **`base_ring` / `port_b` / `port_c`**。`base` は無効値
- **beat mode の首振りは「1拍に1回 ±14°に飛ぶ」だけ。** 遅い曲だと間延びする。
  BPMを貰って**自前で連続的な波を作る**方が滑らかで、細かさも調整できる
- **beat mode は音を出さない。** 首もLEDも自前で駆動し、beat mode は拍の検出だけに使うのが自由度が高い
- **beat mode は本体のマイクで周辺音を拾う。** 音源は何でもよく、空気を伝わればいい
- 実機の listen は **30秒でタイムアウトし、約3秒後に再開する**。
  その空白を「音が止まった」と誤判定しないこと（`capture_state` を見る）
- **`follow_pose_stream` と beat mode は首を取り合う。** 調停は gateway に無い。
  つまみを触っていない間は pose を送らないことで解決した
  （送り続けると「正面を向け」を毎秒20回投げて踊りを潰す）
- 確信度 = **密度 × 安定度**。拍が取れていても**BPMが揺れると0になる**
- DJ向けの設定は**非対称にする**：始まりは1回の観測で即座に、終わりは8秒以上待つ。
  ブレイクダウンで止まらないように
- **表情中はまばたきを止める。** まばたきのコマは「素の顔」なので、表情が壊れる。
  表情ごとのまばたきが要るなら `matrix` モード（90枚・3.3MB）
- **stackchan-mcp は音声も踊りも既に持っている**（2026-09-08 に実物で確認。`architecture.md` の記述が古かった）
- gateway は WebSocket 8765 / 写真HTTP 8766、認証は `STACKCHAN_TOKEN`
- **接続先の解決順序**：NVS `websocket.url` → mDNS（**NVSが空のときだけ**）→ ビルド時デフォルト → 失敗。その後 `websocket.fallback_url` を試す
- **`stackchan-mcp --no-mdns` で名乗りを止められる。** mDNS の advertise を自作する必要はなかった
- 複数の gateway が名乗っていると、ファームは1回の browse で全部を順に試す。**壊れないが繋ぎ先は不定**
- 公式の推奨構成表に「**LAN自動検出（primary空）+ relay fallback**」がある。自分たちの設計と同じ
- **NVS はファームを焼いても消えない。** 出荷時ファーム由来の `wss://api.tenclass.net/...` が残る
- プリビルドのままでも、**WiFi設定UI の Advanced タブ**から `websocket.url` を上書きできる
- **接続には2段の関門がある**：① OTA問い合わせ（`ota_url`）→ ② WebSocket（`websocket.url`）。
  ①で「未登録」と言われると6桁コードが出て**②まで到達しない**。`scripts/ota_stub.py` で抜ける
- **NVS の中身はシリアルから直接読める**：`esptool read-flash 0x9000 0x6000 nvs.bin` → `strings`。
  「設定が保存されたか」を推測せずに確認できる
- 設定モードに戻すには **NVS 領域を消す**：`esptool erase-region 0x9000 0x6000`。
  ファーム本体は消えない。**消す前に read-flash で退避しておく**
- 実機の状態はシリアルで見える。DTR/RTS を叩けばリセットもかかるので、**起動ログを頭から読める**
- 焼き方は `esptool.py --chip esp32s3 --port /dev/cu.usbmodem* -b 460800 write_flash 0x0 merged-binary.bin`
- **gateway にはデーモンモードがある**：`stackchan-mcp serve --transport streamable-http` → `http://127.0.0.1:8767/mcp`。
  **複数の MCP クライアントが同じ実機を共有できる**（自作アプリと Claude Code が共存できる）。
  stdio モードは単一クライアント専用
- サーボは **2軸だけ**（yaw ±90° / pitch 5〜85°）。増やせない。
  表現を増やすなら**トルク・まばたき・口・LED・アバター**の側で稼ぐ
- アバターは **RGB565 にアルファが無い**。目や口だけを透過で書き出すと、
  そのフレームが選ばれた瞬間に崩れた顔が出る。**どの1枚も画面全体の完成画**であること
- **DDJ-FLX2 はクラスコンプライアント。** ドライバ不要で macOS に USB MIDI として出る
- **外付けLEDテープは M5Stack 純正 `A093`**（0.5m / 30LED / SK6812 / IP65 / ¥1,144）。
  **HY2.0-4P アダプタケーブル同梱**なので追加購入は不要。赤=VCC 白=GND 緑=データ。
  **全開 1.8A** なので明るさ上限が必須。Port B(GPIO9) / Port C(GPIO17) の2系統、各256個まで
- **rekordbox の Ableton Link は Performance モードのみ。** Export モードでは動かない

## リファクタリングで得た学び（2026-09-08）

### ベストプラクティス

- **リファクタは「同じ結果が出ること」を数字で証明してから終わりにする。**
  旧コードを丸ごとコピーして残し、新旧に同じ時刻・同じ状態を流し込んで差を測った。
  4種のBPM × 4000点 = **16000点で最大差 0.0000000000 度**。
  「たぶん同じ」ではなく「1度も違わない」と言える状態にしてから旧コードを消す。

- **テストは grep ではなく「振る舞い」で書く。**
  最初 `"scan" が console.py にあるか` を文字列検索で見ていた。
  これは置き場所を変えただけで落ちる＝リファクタの邪魔をする。
  「scan と sway が違う角度列を出すか」に変えたら、**移動しても落ちず、中身が空なら落ちる**。

- **状態を持つメソッドは、引数だけで決まる純関数に切り出す。**
  振り付けは `self.bpm` `self._phrase` `self._groove_now` に依存していて、
  **実機を繋がないと確かめられなかった**。純関数にした瞬間、全フレーズの全時刻を
  0.3秒で検証できるようになった。

### アンチパターン

- **可動範囲を知らずに角度を作る。**
  `sway` フレーズが pitch差 49.8度を返していた。上限は40度。
  **超えた分は gateway が黙って丸める**ので、コードを読んでも気づけない。
  「頷きが弱い」の原因の一つがこれだった。**テストが見つけた。手では無理。**

- **リファクタで“ついでに”仕様を変える。**
  頷きの深さは `nod_deg`（ノリで薄めない）を使っていたのに、
  切り出す時に `nod`（ノリで薄まる）に統一しかけた。読みは綺麗になるが**動きが変わる**。
  `dip` 引数を足して元の挙動のまま残した。**綺麗さより同一性が先。**

### ノウハウ

- 上限は**呼ぶ側と呼ばれる側の両方**に定数として置き、テストで一致を確かめる。
  片方だけだと、いつか黙ってずれる。
- 首を動かす経路が5つあり調停役がいなかった。`HeadArbiter` を作って
  **つまみ > キメのポーズ > 踊り** の優先順を1箇所に集約した。
  今日の重いバグはほぼ全部この「誰が首の持ち主か曖昧」から出ていた。

### モジュール分割の学び（同日）

- **分割で一番危ないのは import 漏れ。しかも実行時にしか落ちない。**
  1218行を9ファイルに割ったあと、`--help` は通り、テストも通った。
  だが `pyflakes` をかけたら **未定義名が30個**あった（`MODE_DJ` `mido` `_scale` …）。
  「曲を流してPLAYを押した瞬間に落ちる」類のバグが埋まっていた。
  **分割したら必ず静的解析。import が通ることは動くことの証明にならない。**

- **共有する定数は1ファイルに集めて、そこから配る。**
  可動範囲 `YAW/PITCH` を複数ファイルに書き写していたら、いつか黙ってずれる。
  `constants.py` に集約し、**gateway 側と同じ値であること**をコメントで固定した。

- **ソースを文字列検索するテストは、分割のたびに落ちる。**
  今日3回落ちた。落ちた3回とも**バグではなく、テストが置き場所を見ていた**だけ。
  「`app/dj/**.py` 全部を1本につないで探す」か、「実際の出力で見る」に直した。
  **テストが見るべきは、どこにあるかではなく、あるかどうか。**

- **照合は「メソッドの本文が1行も変わっていないか」まで見る。**
  API（メソッド名と引数）が一致していても、中身が欠けていたら意味がない。
  45個のメソッドを本文で突き合わせて、差分ゼロを確認してから旧コードを消した。

### 設定ファイルと自己検証（同日）

- **引数が47個あると、会場で詰め直せない。**
  その場のノリを詰めるのに毎回47個打つのは無理で、前回どう詰めたかも残らない。
  `config.toml` に移し、**CLI > toml > コードの既定値** の順で強くした。
  現場で1個だけ試すときはファイルを開かずに済む。

- **設定ファイルの綴り間違いは、黙って無視されるのが一番こわい。**
  `full-levl` と書いても動いてしまうと、「効かないなあ」と何十分も溶かす。
  知らないキーは**起動時に止める**。似た名前も出す。

- **移行は「同じ値になること」を照合してから。**
  58項目を、旧CLIコマンドと新 config.toml で突き合わせて全一致を確認した。

- **`--verify` を入れた。目で見て判断する前に、機械に数えさせる。**
  10秒ぶん実際に送った角度を測り、可動範囲・真下向きを判定して終了コードを返す。
  9月8日は「直しました」と3回報告して3回とも直っていなかった。
  **ソースを読んでも分からない。送っている値を見るまで分からない。**

- **検証ツール自身も検証する。**
  偽のストリームを立てて、事故と同じ値（pitch差45＝真下、yaw 999）を流し込み、
  **ちゃんと落ちること**を確かめた。判定部分は純関数に切り出してテストに固定した。

- **後片付けだけ済ませて `os._exit` で落とす、が正解のときがある。**
  ws サーバと MIDI のループは cancel しても素直に畳まれず、待つと固まった。
  診断ツールは「確実に終わる」ことの方が大事。

### 立ち上げ・立ち下げ（2026-09-08）

**「Ctrl-C で終了」と画面に出していたが、pkill では片付けが1つも走っていなかった。**

- **止め方が2通りあるなら、2通りとも試す。**
  Ctrl-C（SIGINT）は通っていた。`pkill`（SIGTERM）は即死で、
  beat mode は回りっぱなし、ストリームも購読したまま残った。
  片方しか試していなかったので、半分壊れていることに気づけなかった。

- **`async with websockets.serve(...)` は、抜けるとき接続が閉じるのを無期限に待つ。**
  gateway が繋ぎっぱなしなので、**永遠に畳まれない**。
  `serve()` を await で受けて、`finally` で `close()` + 時間を区切って待つ形にした。
  これが `--verify` が終わらなかった原因でもあった（当時は `os._exit` で誤魔化していた）。

- **片付けには必ず制限時間をつける。**
  相手（gateway・実機）が応答しないとき、待ち続けると止まらなくなる。
  **落ちないより、片付け損ねる方がまし。** 8秒で打ち切って、何が残ったか出す。

- **畳めなかったループの名前を出す。**
  「なんか終わらない」では調べようがない。`★ 畳めなかったループ: ws_server` と出せば、
  次に同じことが起きたとき30秒で分かる。

- **フラッシュには書いていない。**
  表情の転送先は PSRAM で、起動のたびにフラッシュへ書く箇所は無い。
  書き換え回数を気にする必要はない。

#### 立ち下げでやること（順番に意味がある）

1. `beat_mode_stop` — 先に音を聴くのをやめる。後回しにすると踊り続ける
2. ストリームの購読解除 — gateway が死んだ相手を掴み続けないように
3. 首を正面へ — 踊りかけの角度で放置しない
4. 待機の顔へ
5. サーボの脱力は**実機側の自動脱力（既定8秒）に任せる**。こちらで切らない

### 常駐化（2026-09-08）

**「起動する」という作業を無くすのが、いちばん効くUX改善だった。**
手順を分かりやすく書くより、手順を消す方がいい。

- **console も常駐させてよい。** 起動時のモードが OFF なので、置いておいても何もしない。
  PLAY を押したときだけ反応する。**「待っている」状態を常態にする。**

- **実機を待つ時間は、常駐なら無限でいい。**
  `--wait-device 0` で、実機が来るまでずっと待つ。
  **電源を入れた瞬間に繋がる**ので、順序を気にしなくてよくなる。
  （20秒で諦める設定は、手で起動するときのため）

- **プロセスを名前で探すと見つからないことがある。**
  gateway は `ps` から見るとただの `Python` で、`pkill -f stackchan_mcp` に引っかからない。
  結果、古い gateway が生き残り、launchd 版が
  `device already owned` で20秒ごとに起動と失敗を繰り返していた。
  **ポート番号で探す**のが確実（`lsof -nP -iTCP:8767 -sTCP:LISTEN -t`）。

- **同じ Mac に別プロジェクトの Python が居る。**
  ポートで探すこと自体が、巻き添えを防ぐ手でもある
  （8765 は別プロジェクトが使っている。名前で殺すと巻き込む）。

- **復帰は実際に殺して確かめる。**
  `KeepAlive` を書いただけで安心しない。`kill -9` を両方に撃って、
  20〜40秒で戻ってくることを見た。

### 健康診断（2026-09-09）

**「中身」と「入口」を分けると、入口が増えても作り直しにならない。**

doctor は中身。入口は Mac のコマンド／スマホ（HTTP）／頭を撫でる、と増えていくが、
呼ぶ関数は1つに保つ。`run()` は結果を返すだけで、表示も引数解析もしない。
**テストで「入口の都合を中身に持ち込まない」ことを固定した**（argparse / print / sys.argv が
`run()` に出てきたら落ちる）。

- **毎回出る警告は、いずれ誰も読まれなくなる。**
  表情が入っているかは問い合わせる手段が無い。最初これを毎回 △ で出したが、
  正常時にも必ず出る警告は「狼少年」になる。**検査項目から外し、注記に落とした。**

- **直したら「直った」と表示する。**
  直したのに × のまま残していて、全部直したのに
  「直っていないものがあります」と出ていた。**当日これで混乱する。**
  ✓（直した）を状態として持たせ、件数を出すようにした。

- **日本語は表示幅2で数える。** 文字数で揃えると桁がずれる。読めない表は読まれない。

- **診断ツールは、わざと壊して試す。**
  購読を切って beat mode を止めてから点検→修復を通した。
  「異常時に正しく異常と言うか」は、正常時のテストでは分からない。

#### いま点検している9項目

表情のデータ（ファイルとサイズ）／console が動いているか／DJ機材／gateway／実機の接続／
音の取り込みと音量／pose 購読／LED 購読／首が可動範囲か

`--fix` で直せるのは、購読のやり直し・beat mode のかけ直し・表情の入れ直し・console の起動。

### アーキテクチャの立て直し（2026-09-09）

**「モグラ叩きになっている」と言われた。その通りだった。**

- **同じ形のバグを1日に2回出したら、それは機能の不足ではなく設計の欠落。**

  表情19箇所/5ファイル、瞬き12箇所/4ファイル、持ち主なし。

- **設計文書を先に書き、テストにして、コードを寄せる。**
  ①`docs/architecture.md` に不変条件を7つ書く
  ②`tests/test_architecture.py` に写す（**35件の違反が機械的に出た**）
  ③赤を消していく
  **文書が規範で、コードが従う。** 逆をやると文書はすぐ嘘になる。

  「顔を出す」「N秒後に戻す」を各所が叩いていたのを、

  送りっぱなしだと、外から乱されたときに戻らない。20秒ごとに送り直すことで、

  gateway 側の beat mode にも首を動かす機能があり、
  実は起動直後に切られて以後ずっと OFF のまま console が踊らせていた。
  **つまり「常に切る」が正しい。** 暴走は「本来ずっと切るものが入った」事故だった。
  当初 `DJ なら有効` と書いた設計を、実装を読んで訂正した。

  静的解析では見つからない。`tasks.append(con.X())` の X が実在するかを試験に足した。

### LEDの演出を実機で詰める（2026-09-10）

**外付けテープ（M5Stack A093 / 30LED / Port B）を足して、Alan Walker のライブ風に。**

#### 数字は、画面では決まらない

sweep の1周を**8回**動かして決めた。

```
0.94秒 → 0.70(速すぎ) → 1.17(遅い) → 1.05 → 0.98 → 0.91 → 0.81 → 0.65 → 0.45 ★
```

- **「ちょうどいい」は机上で出せない。**実機で見て、少しずつ動かすしかない
- 私は 0.70 を「速すぎて点滅に見える」と判断したが、**0.45 で問題なかった**。
  速さの限界は**尾の長さで変わる**（尾が長いと、速くても目が追える）。
  **一度の観察で境界を決めつけない**
- 最後は**1拍で1周**に落ち着いた。**拍と揃う数字は気持ちよく感じる**

#### 「派手」を数字で固定する

感想では測れないので、**8件のテストに翻訳した。**

| 仕様 | 数字 |
|---|---|
| 焼けるように光る | ピーク 220 以上 |
| 点きっぱなしにしない | 最小 60 以下・落差 160 以上 |
| 端から端まで走る | 光が触れた範囲が全長の6割以上 |
| 線に見える | **強く光る粒**が4割以下（地明かりは別に数える） |
| チカチカ | 1拍あたり3回以上の明滅 |

**「線」と「地明かり」を分けて測る**のが要点だった。
拍の頭でうっすら全体が光るのは演出として正しいが、
**強い粒**が広がると線ではなく面になる。**測る対象を間違えると、良い演出を禁止してしまう。**

#### 測り方を2回間違えた

- **全灯型と走査型を混ぜて測った。**落差で殴る模様と、動きで見せる模様は、測る指標が違う
- **時計に頼って測った。**「どの拍を見ているか」が実行のたびに変わり、
  ビルドアップの加速を測れなかった。**拍を自分で進める**形に変えたら測れた
- 点滅が速すぎて**標本化が折り返していた**。1拍20点で16回の明滅は数えられない

#### 電流の制約が、演出を良くした

サビの「白のべた塗り2.5秒」は Grove の連続供給（1A）を超える。
**点滅に変えたら、電流が下がり、見た目も強くなった。**
**制約が正解を教えてくれることがある。**

#### 乱数を使わない

粒がバラバラに飛ぶ模様で、乱数を使わず**拍から決まる**ようにした。
毎回違う絵だと「演出」ではなく「ノイズ」に見える。
**同じ拍で同じ場所が光ると、繰り返すうちにリズムとして認識される。**

### 背景スクリーンをつなぐ（2026-09-11）

**「スタックチャンが指令している」を、演出ではなく事実にした。**

```
実機のマイク ──▶ gateway ──▶ console ──▶ iPad の背景
```

背景を動かしているのは、**実機が聴いた音そのもの**。
「連動しているように見せる」のではなく、**本当にその経路で動いている。**
当日そのまま説明できる。

- **写真を見せてもらったら、要素は3つしかなかった。**
  ①二進数が降る ②シアンの発光とにじみ ③下の帯。
  **「なんとなく格好いい」を、数えられる要素に割ると作れる。**

- **色は1箇所から採る。** テープと画面で色が食い違うと、途端に嘘くさくなる。
  同じ `_series_name()` を両方が呼ぶ形にした。

- **サーバは1本にした。** 背景と、あとで作るスマホの操作パネルとペルソナボードは、
  全部同じ土台に乗せる。**分けると3回作ることになる。**

- **絵はブラウザに任せ、サーバは状態だけ渡す。**
  送るのは9項目（BPM・拍の位置・色・踊り・サビ・モード・会話）。
  **毎拍たくさん送ると、iPad より先にネットワークが詰まる。**

- **拍は「秒」ではなく「拍の中の位置 0..1」で渡す。**
  受け手が自分の描画速度で補間できる。20Hz で送っても 60fps で滑らかに動く。

### 会場で動くようにする（2026-09-11）

**家で動くことと、会場で動くことは別。** 家の前提を3つ剥がした。

| | 家 | 会場 |
|---|---|---|
| 母艦 | Mac Studio | **MacBook** |
| 網 | 自宅Wi-Fi | **iPhone のテザリング** |
| IP | だいたい固定 | **毎回変わる** |

#### 変わらない名前を1つ作って、そこに全部ぶら下げる

`stackchan.local` を mDNS で名乗る。**どの Mac で動かしても同じ名前**になる。
iPad は毎回 `http://stackchan.local:8779/` を開けばよい。
IP が変わったら**自動で名乗り直す**（5秒ごとに見ている）。

- **機械名（`unis-Mac-Studio.local`）を使わない。**会場では MacBook になるので、
  そのまま使うと必ず壊れる。**自分で名乗るから、機械に依存しない**

#### 「実機より先に画面を立てる」— 順序の設計

**致命的な順序を1つ見つけた。**

```
直す前   実機を待つ（無限）→ … → 画面サーバ起動
         ロボットの電源を入れるまで iPad が真っ暗
```

設営中こそ画面を出しておきたい。**実機に触らずに組める部分を先に組む。**
`Console` は状態を作るだけなので、実機なしで構築できる。**そこを分けた。**

> **「立ち上げ順序を自由にする」は、依存の少ない順に並べ替えること。**

#### 名乗れなくても止めない

mDNS が失敗しても console は動き続け、**IP で開ける旨を出す**。
テザリングによっては mDNS が通らないことがある。
**degrade して動かす。全部か無かにしない。**

#### 非同期の中で同期APIを呼ぶと固まる

`zeroconf` の同期版を asyncio の中から呼んだら **TimeoutError** で落ちた。
自分のループの完了を待つため。**非同期版（`AsyncZeroconf`）を使う。**
ライブラリに async 版があるときは、理由があって用意されている。

#### QR を端末に出す

会場で URL を手入力させない。**起動時に端末へ QR を描く。**
iPad のカメラで読めば終わり。**打ち間違いという失敗経路が丸ごと消える。**

### 会話を通した（2026-09-12）

**計画していた別サーバ（xiaozhi-esp32-server）は要らなかった。**

gateway が既に `listen`（聞き取り）と `say`（発話）を持っていた。
**「詰まりそうな関門」が、調べたら存在しなかった。**

> **計画の前に、いま手元にあるものの棚卸しをする。**
> 半年前の設計メモに書いてある「必要なもの」は、もう不要になっていることがある。

- Docker も x86 の問題も起きなかった。**最大のリスクが調査だけで消えた**

#### 日本語の聞き取りが崩れた。原因は3つとも「音の渡し方」

「ファームってなんですか」→「あー塗ってなんですか」「パー持って何ですか今 本性 手措置が」

| 手 | 効果 |
|---|---|
| **無音を捨てる**（VAD） | 8秒録って喋っているのは2秒。**残りの無音に幻聴が出ていた** |
| **音量を持ち上げる** | 実機のマイクは声でもピーク **0.055**。Whisper には小さすぎた |
| **当日の語彙を先に教える** | これが一番効いた。「カーム」→「ファーム」で一致 |

- **モデルを大きくしても直らなかった。**`medium` は56秒かかって、内容も崩れたまま。
  **遅くて精度も出ないなら、原因はモデルではない**
- **録れた音を取り出して、自分で文字起こしして切り分けた。**
  「音が悪い」のか「経路が悪い」のかは、**音を聞くまで分からない**

#### 答えが的外れだったのは、知識が無かったから

「ファームってなんですか」→「農業を主な仕事として行う施設」

**前提知識を渡したら直った。** しかも **3Bのモデルで 0.7秒**。
14B に上げても答えは良くならず、遅くなるだけだった。

> **モデルの大きさより、渡す知識。**
> 小さいモデルに正しい前提を渡すほうが、大きいモデルに丸投げするより速くて正確。

#### 実機の制約：踊りと会話でマイクを取り合う

    beat mode is already using the device microphone

同時には使えない。**時間割で分ける**（触る＝踊る／もくもく＝会話）。
マイクの受け渡しは console が持つ（beat mode の持ち主だから）。

#### 「いつ話せばいいか」が分からないと空振りする

合図なしで録ると、2回に1回は無音のまま終わった。
**LEDを緑にしてから録る。**「緑＝話していい」は参加者に配る紙にも書いてある。
**機能ではなく合図が足りていなかった。**

### 直らないものを追いかけすぎた（2026-09-12）

タッチセンサの不安定さを、**対話で15秒ずつ試しながら**追い続けて、
本人の時間を大量に使った。結論は出なかった。

#### 何が起きていたか

- 実機は撫でられると**通知を送る**（`stackchan-event`）
- `get_touch_state` は**その通知を保存しない**ので、ポーリングでは永遠に `idle`
- 通知の届け先は**既定で全部 false**。開けないとどこにも届かない
- **通知は「指を離した瞬間」に届く。** 撫でている間は来ない
  （250899ms＝4分11秒の記録があった）
- そして**届いたり届かなかったりする。原因は未特定**

#### 学び

- **押し出されるものを、引きに行っても取れない。**
  取れないとき「壊れている」より先に「窓が違う」を疑う
- **沈黙は故障と見分けがつかない。**
  既定で全部 false の通知は、開け忘れても何も言ってくれない
- **押し出し型は「いつ押し出されるか」まで確かめる。**
  離すまで来ないと知らずに、「センサが壊れた」と判断しかけた

#### 進め方の学び（こちらが本題）

**対話で1つずつ試す形は、相手の時間を使う。**
「15秒撫でてください」を10回以上やった。**これは私のデバッグに人を使っている。**

> **再現しないものは、対話で追わない。記録係を置いて、普段使いのなかで溜める。**

#### ★もう一つの誤り：勝手に「使わない」と決めた

「会話の起動に使わない」を、いつのまにか「**当日使わない**」に広げて報告した。
**要否を決めるのは実装者ではない。**

**撫でて反応を楽しんでもらうこと自体が、掴みの中身。**
「最重要：触らせること」がそれ。会話の入力をスマホに移すのとは別の話。

> **困難に当たったとき、勝手にスコープを縮めない。**
> 「難しい」と「要らない」は別。**要否を決めるのは本人。**

#### 副産物：撫でる反応は作り込めた

| 撫で方 | 反応 |
|---|---|
| 久しぶりにポン | 驚く |

# ファームを焼き替えて頭なでを直した（2026-09-12）

## 何が起きていたか

**20秒間ずっと撫でて、検出は1回。**

原因は上流の PR #374（`kisaragi-mochi/stackchan-mcp`）にそのまま書いてあった。
**Si12T の感度レジスタを、ドライバが初期化時に一度も書いていなかった。**
チップは電源投入時の既定しきい値のまま動いていて、
**頭の外殻ごしではほぼ反応しない。**

これで、記録に残っていた謎の数字も説明がついた。

```
stroke  250899ms   ← 4分11秒の「撫で」
stroke   96700ms
```

しきい値が合わずに張り付き、**指を離すまで通知が出なかった**だけだった。

## ベストプラクティス

### 「効いていない設定」は、動かないより見つけにくい

書かれなかったレジスタは、エラーを出さない。**既定値で動いてしまう。**
壊れているなら気づくが、**鈍いだけなら「そういうものか」で済んでしまう。**

PR は直すついでに、**書いた値を読み戻して起動ログに出す**ようにしていた。

```
Si12T: init OK: ctrl=0x03 out1=0x00 sens12=0x02 sens34=0x00 (sleep cleared)
```

> **設定したことと、設定が効いていることは別。読み戻して初めて確かめたことになる。**

### 「直った」と言えない試験は、直ったことを確認できない

焼いた後、比較器は **「問題なし。変化なし」** と報告した。
実際は 1回 → 15回 に直り、聞き取りも正しくなっていた。

比較器が **×→○ の反転しか見ていなかった**から。程度の変化に言葉が無かった。

**デグレを見つける道具として作ると、改善を見落とす。**
両方向を等しく扱うようにして直した。

### 数字には向きがある

同じ「value」でも、**秒数は小さいほど良く、検出回数は多いほど良い。**
一律に「小さいほど良い」で比べていたので、
**1回 → 15回 の改善を「劣化」と報告する状態だった。**

> **直った瞬間にデグレと叫ぶ試験は、無いより悪い。**

ついでに、回数に「秒」の単位が付いて表示されていたのも直した。
**単位を間違えた数字は、読む人の判断を変える。**

## ノウハウ

### OTA構成なら、焼くのは怖くない

```
ota_0   0x20000    いま動いている
ota_1  0x410000    ← ここに焼く
assets 0x800000    表情の素材。appだけ焼けば触らない
```

**使っていない側に焼いて、otadata で起動先を切り替える。**
戻すのは otadata を消すだけ。**appを上書きしないので、失敗しても前のまま起動する。**

`merged-binary.bin` は **NVS を消す**（WiFi設定が飛ぶ）。使うのは `xiaozhi.bin`（app のみ）。

otadata の中身（実測で検算した）:

```
seq(4) + label(20) + state(4) + crc(4) = 32バイト
起動するスロット = (最大の有効 seq - 1) % 2
crc = zlib.crc32(seqの4バイト, 0xffffffff)     ← ★変種が多いので実機の値で確かめる
```

### ESP-IDF は入れなくていい

上流の CI が Docker でビルドしている。**同じことを手元でやればいい。**

```bash
docker run --rm -v "$PWD":/project -w /project \
  espressif/idf:v5.5.2 python ./scripts/release.py stackchan
```

ただし **Docker から実機の USB には届かない**（macOS + colima）。
焼くのは母艦側から `esptool`。**ビルドと書き込みは別の場所でやる。**

### フォークからの PR には CI の成果物が無い

`gh pr checks` に Build が出てこない。**焼けるバイナリはどこにも落ちていない。**
自分でビルドするか、フォークして自分の Actions で回すかの二択になる。

## アンチパターン

### 試験が本番の構成を壊しながら測る

`device_check.py` は首と LED を直接書いていた。
ところが console は **唯一の書き手**（architecture.md I2）で、20秒ごとに全部を書き直す。
**二人が書けば、測った値が誰のものか分からない。**

そうしたくなる理由がある。**試験は「実機を直接叩くのが確実」に見える。**
実際には、確実なのは**書き手が一人のときだけ**。

かといって console を止めるだけだと、ストリーム試験の接続先が消えて **偽の×** が出る。
**それを基準にすると、焼いた後の比較が全部狂う。**

直し方: 試験台が **console を止め、自分で WS サーバを立て、終わったら必ず戻す。**
焼く前と後で**同じ条件**になる。比較が意味を持つのはそのときだけ。

### 試験の合図を端末に出す

`>>> 20秒間、頭を撫でてください <<<` を print していた。

# 背景の作り込みで分かったこと（2026-09-13）

DJイベントの背景（有機ELウォール＋照明）を、実物の写真を見ながら詰めた記録。
**何度もやり直したので、間違え方に型がある。**

## ベストプラクティス

### 「配れた」と「描けた」は別

`HTTP 200` を見て「動きました」と報告し、画面は真っ暗だった。
`stepHeads is not defined` で描画ループが即死していた。

**canvas を偽物にして draw を回す試験**を作ったら、3秒で分かるようになった。
状態は本物と同じ WebSocket 経由で流す（VM の中の `let S` は外から差し替えられない）。

> **人の目でしか確かめられない部分と、機械で分かる部分を分ける。**
> 「きれいか」は人。**「描けたか」「幾何が合っているか」は機械。**

### 目で見ても気づけない性質は、数字で見張る

遠近が線形に戻る／左右が非対称になる／灯体が増えすぎる。
どれも**画面を見ても気づきにくい**。`__debug` を露出して19項目を検算するようにした。

## アンチパターン

### アフィンを遠近と呼ぶ

短冊に切って**高さだけ**縮めていた。これはアフィン変換で、遠近ではない。
**奥へ行くほど横方向も詰まる**のが、遠近のいちばん強い手がかり。
横が詰まっていないので、壁ではなく**垂れ幕**に見えていた。

```
高さの倍率   s(u) = k / (k + u(1-k))
元画像の位置 su   = k·u / (1 - u(1-k))
```

★式を書いたら**端の値を検算する**。一度 `1/k` になっていて、
**奥へ行くほど広がる**壁ができていた。

### 動かして派手にしようとする

「派手さがない」と言われて、**光源を速く揺らした。** 逆だった。
実際のムービングヘッドは**キューへ素早く動いて、止まっている。**
派手さの正体は**シャッター**で、灯体は静止したまま光だけが刻む。

★**ゆらゆら揺らすと、必ず安っぽくなる。** 太さも色も、点いている間は動かさない。

### 暗い場所に輪郭線を引く

トラスも灯体も、線で描いていた。**暗い会場で輪郭は見えない。**
見えるのは**光を遮る黒い抜け**と、**光が当たった面**だけ。

### 素材が光に反応しない

床・天井・柱を一様な黒で塗っていた。**ビームが当たっても何も起きない。**
現実は、当たった面が**光の色**になる。反射を足したら、一気に部屋になった。

### 層の順序を物理と合わせない

コードを最後に描いていたので、**LEDウォールがライトの手前に浮いていた。**
奥から：**ウォール → 空気中の光 → トラスと灯体**。

## ノウハウ

言葉で「派手に」「安っぽい」を往復していたが、写真を見た瞬間に
