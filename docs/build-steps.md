# 第1段　身体を自分のコードで動かす（会話なし）

**ゴール：自分の書いたコードで首が回る。**

## Step 1. gateway を Mac で起動する

- **目的**：ESP32 の接続先を作る。**先にサーバーを立ててから焼く**
- **やること**：stackchan-mcp を clone、`uv run python -m stackchan_mcp` で起動
  - Python だけなので **Apple Silicon の問題は起きない**
  - `gateway/.env` に `STACKCHAN_TOKEN` を設定
- **終わったと言える条件**：8765 で WebSocket が待ち受けている
- **詰まりどころ**：ポートが埋まっていないか。ファイアウォールで弾かれていないか

## Step 2. ファームを焼く

- **目的**：接続先を自分の Mac に向ける
- **やること**：
  1. `merged-binary.bin` を esptool で書き込み（**足側の USB-C**、データ通信対応ケーブル）
  2. 起動後、本体の WiFi 設定UI で **2.4GHz** に接続
  3. まず `websocket.url` に `ws://<MacのLAN IP>:8765/` を入れて疎通させる
  4. ★ 通ったら **`websocket.url` を空にして mDNS で見つかるか試す**（`_stackchan-mcp._tcp.local.`）
     → 効けば**以降URLを一切触らなくてよくなる。最優先の確認項目**
  5. ★ `websocket.fallback_url` に自宅の Funnel を入れる
  6. ★ **fallback の挙動を実測**：マスタを落とす → 何秒で fallback に行くか →
     マスタを上げる → **自動で戻るか**。3分で終わる → [master-and-hybrid.md](master-and-hybrid.md)
- **終わったと言える条件**：gateway のログに ESP32 が接続してきたと出る
- **詰まりどころ**：
  - ポートが見えないときは**ダウンロードモード**（RST を3秒長押し、隣のLEDが緑になったら離す）
  - 5GHz には繋がらない
  - **ここから喋らなくなる**（想定通り）

## Step 3. コマンドを叩いて動かす

- **目的**：**最初の手応え。ここが一番うれしい瞬間**
- **やること**：Claude Code を MCP クライアントとして繋ぎ、順に叩く
  - `get_status` → 生きているか
  - `move_head` → **首が回る** ★
  - `set_led` / `set_all_leds` → 12個のLEDが光る
  - `set_avatar` / `set_blink` / `set_mouth` → 表情が変わる
  - `take_photo` → 写真が撮れる
  - `get_touch_state` → なでたのが取れる
- **終わったと言える条件**：**自分の指示で首が回り、写真が撮れた**
- **メモしておくこと**：`move_head` の角度の単位と可動範囲。後で全部これを使う

# 第2段　スマホから、外から操作する

**ゴール：外出先のスマホから、家のスタックチャンを動かす。**

## Step 4. Mac に Web操作パネルを立てる

- **目的**：スマホから触れるようにする。**イベントのペルソナボードの土台にもなる**
- **やること**：FastAPI + HTML 1枚。gateway に中継するだけ
  - ボタン：首 左/中央/右、表情4つ、LED色、写真を撮る
  - 凝らない。**当日落ちない方が偉い**
- **終わったと言える条件**：**同一LANのスマホで開いて、ボタンを押すと首が回る**
- **詰まりどころ**：Mac の LAN IP は変わることがある。固定するか mDNS を使う

## Step 5. Funnel で外に出す

- **目的**：家の外から操作する
- **やること**：
  ```bash
  tailscale funnel --bg --https=443 http://localhost:<Web UIのポート>
  tailscale funnel status
  ```
  - Funnel が待てるのは **HTTPS の 443 / 8443 / 10000 のみ**
- **終わったと言える条件**：**モバイル回線のスマホから開いて、首が回る**
- **詰まりどころ**：`--https=443` は1つしか使えない。Web UI と gateway で取り合う
- ⚠️ **URLを知っていれば誰でも触れる。** トークンで守るか、使わないときは `off` にする

## Step 6. 遠隔ワークベンチを完成させる

- **目的**：以降を全部リモートで進められるようにする
- **やること**：Webカメラを本体に向ける／スマートプラグでUSBハブの電源を握る／`keep-awake.sh` 常駐
- **終わったと言える条件**：**外から焼き直して、元に戻すまでを1回通しでやれた**
- ⚠️ **これを家にいるうちに1回やる。** → [remote-workbench.md](remote-workbench.md)

# 第4段　音楽と踊る

**Step 11 は今すぐできる。実機もサーバーも要らない。**

## Step 11. MIDI をただ表示する（★並走可・今日できる）

- **目的**：FLX2 が何を出すか知る。**ここで機種の癖が全部わかる**
- **やること**：`mido` で受信して print するだけ。`app/dj/midi_dump.py`
- **終わったと言える条件**：**つまみを捻ると、どのCC番号が0〜127で動くか一覧できた**
- **詰まりどころ**：rekordbox が掴んでいる最中に同時に読めるか。ここで実測できる

## Step 12. つまみ → 首

- **やること**：CC値 0〜127 を首の角度に線形マッピング。gateway の WebSocket を直接叩く
  - **MCPツール経由にしない。** 連続追従にはオーバーヘッドが乗る
  - 間引き（30〜50msに1回）とデッドバンド（小さい変化は無視）を必ず入れる
- **終わったと言える条件**：**つまみを捻ると、遅れずに首が付いてくる**
- ⚠️ サーボが唸り始めたら間引きが足りない

## Step 13. PLAY・パッド → 笑う

- **やること**：`set_avatar` / `set_mouth` を叩く。数行で終わる
  - PLAY → 笑う ／ 盛り上がり → もっと笑う ／ CUE → 真顔 ／ **曲間 → 眠そう**
- **終わったと言える条件**：**曲を流すと笑い、止めると真顔に戻る**
- **曲間に眠そうにするのを必ず入れる。** ずっと笑っていると置物に見える

## Step 14. リズムを刻む v0（BPM手入力）

- **やること**：PLAY押下を1拍目とみなし、手入力したBPMの周期で首を振る
  - **2拍に1回**。BPM128 の全拍は往復4.3回/秒でサーボが保たない
  - **先読みオフセット**を入れる（拍のジャストに振り終わるよう数十ms早く動かす。実測で詰める）
  - 曲間は止める
- **終わったと言える条件**：**1曲通して、リズムに乗って見える**
- 曲を変えたら打ち直す前提。それで実用になる

## Step 15. リズムを刻む v1（Ableton Link）＋ 低遅延化

- **やること**：
  1. rekordbox を **Performance モード**にして LINK をON（Export モードでは動かない）
  2. Link から BPM と拍位置を取る
  3. **テンポと位相だけを実機に送り、刻むのは実機側にやらせる**
- **終わったと言える条件**：**DJがテンポを触っても踊りがズレない**
- **なぜ実機側で刻むか**：BPM128 の1拍は 469ms。ネットワーク往復が1拍を食う。
  拍を1つずつ送る方式は原理的に成立しない → [dj-sync.md](dj-sync.md)

# ネットワークをいつ本番形にするか

## 原則

**新しい変数は、他が全部固定されたときに1つだけ入れる。そしてその変数を最後に取っておかない。**

- テザリングで開発し続ける → 毎回のデバッグに「回線のせいかも」が混ざる。反復が死ぬ
- テザリングを最後に回す → **「できないやん」の典型**

だから**開発は家のWi-Fi、テザリングは節目で3回だけ**入れる。

## テザリング固有の失敗は3つしかない

| # | 失敗 | いつ分かる | 潰し方 |
|---|---|---|---|
| 1 | 5GHzで繋がらない | 繋いだ瞬間 | 設定 → インターネット共有 → **「互換性を優先」をオン** |
| 2 | **クライアント同士が通信できない（AP isolation）** | 2台以上繋いだとき | **MacBookを親APにする**（下記） |
| 3 | Funnel経由の遅延・帯域 | 実際に会話・操作したとき | モデルを小さく。相槌を先に返す |

**1 は10分で潰せる。2 と 3 は構成の話。** だから 1 だけ先に、極端に早く潰す。

## 入れるタイミング（3回）

### ① Step 2 の直後 — 10分。「繋がるか」だけ

ファームを焼いて Wi-Fi 設定をした流れで、**そのままテザリングにも繋いでみる**。
会話も制御もまだ無い状態なので、**純粋に「ネットワークに乗るか」だけ**が分かる。

確認したらすぐ家のWi-Fiに戻す。ここでの目的は上の表の **1 を潰すこと**だけ。

### ② Step 5 の直後 — 30分。★一番おいしいタイミング

外から制御できるようになった時点。**まだ会話が無いので変数が少ない。**

- スマホがモバイル回線
- 本体がテザリング
- 経路は Funnel

この形で首が回れば、**本番のネットワーク構成が先に検証できたことになる**。
ここで詰まっても、まだ会話サーバーを触っていないので切り分けが楽。

**会話ができてから初めてテザリングを試すと、遅いのが回線なのかモデルなのか分からなくなる。**

### ③ Step 9 — 第二関門そのもの

会話を外から通す。ここは元々テザリング必須。

## 当日の本番構成は「iPhoneテザリング」ではない

DJ連携で **MacBook を持っていく**。ならば MacBook を親APにするのが一番堅い。

```
iPhone ──USB──▶ MacBook ──内蔵Wi-Fiで2.4GHz APを立てる──▶ スタックチャン
                    ▲
              DDJ-FLX2（USB-C）
```

- iPhone は **USBテザリング**で回線を供給するだけ（Wi-Fiテザリングを使わない）
- MacBook の内蔵Wi-Fiを「インターネット共有」で **2.4GHz AP** に回す
- **AP isolation の心配が消える**。MacBook が直接ゲートウェイになるので経路も1つ減る

**つまり iPhone の Wi-Fiテザリングは予備扱い。** 本命は MacBook AP。

ただし ① のテストはやる。**予備が動くことを確認しておかないと予備にならない。**

## DJ連携にテザリングは関係ない

踊りは会場ローカル（MacBook AP 内）で完結する。外に出ない。
テザリングが死んでも**踊りは生きる**。会話だけが死ぬ。

**これは当日の保険設計として重要。** 回線が落ちたら会話をやめて踊りに切り替えられる。
