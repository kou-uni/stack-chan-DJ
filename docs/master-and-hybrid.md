# マスタの切り替えとハイブリッド

**結論：できる。しかも設定1つで切り替わる形にできる。**
そのために仕込みが3つ要るので、先に決めておく。

---

## 切り替えの実体は「ESP32が見に行く先」だけ

スタックチャンが誰をマスタと思うかは、**`websocket.url` という1つの設定**で決まる。
アーキテクチャの変更ではなく、設定の変更。

ただし、この設定を変えるには本体のWiFi設定UIか再書き込みが要る。
**現場でこれをやる羽目になると詰む。** だから触らずに切り替わる形にしておく。

---

## 仕込み① fallback を使う（実質これがハイブリッド）

ファームは接続先を**2つ持てる**。

| 設定 | 中身 |
|---|---|
| `websocket.url` | 主。ここに繋ぎに行く |
| `websocket.fallback_url` | 副。主がダメなら次にここ |
| `websocket.token` | 認証 |

つまり最初からこう入れておけばいい。

```
websocket.url          = 会場の MacBook（ローカル・低遅延）
websocket.fallback_url = 自宅の Funnel（wss://...ts.net/）
```

**家では MacBook を落としておけば、自動的に自宅に繋がる。**
会場では MacBook を上げておけばそっちに行く。**本体に触らずに切り替わる。**

---

## 仕込み② mDNS を使えば URL すら要らない

`websocket.url` を**空にすると**、ファームは `_stackchan-mcp._tcp.local.` を
mDNS で探しに行く。

つまり **同じLANに居るゲートウェイを自動で見つける**。

- 家では Mac Studio がそれを名乗る
- 会場では MacBook が名乗る

**本体の設定を一度も触らずに、置かれた場所のマスタに繋がる。**
※ ただし未検証。Step 2 のときに確かめる。

---

## 仕込み③ ゲートウェイのコードを1つにする ★これが一番大事

**「MacBook用」「Mac Studio用」でコードを分けない。**
同じものが両方で動くようにして、**違いは設定ファイルだけ**にする。

```yaml
# gateway config
llm:
  endpoint: http://localhost:11434      # 自宅なら Mac Studio の Ollama
  # endpoint: wss://<node>.ts.net/...   # 会場なら自宅へ投げる
dance:
  enabled: true                          # 近い方の Mac だけ true
```

分けた瞬間に、**片方でしか直していないバグ**が生まれる。当日それを踏む。

---

## ハイブリッドの本命の形：MacBook が中継する

「会話は自宅、踊りは会場」を実現するのに、
**ESP32 から2本の接続を張る必要はない**。近い方の Mac が中継すればいい。

```
スタックチャン ──WS 1本──▶ MacBook
                              ├─ 踊り・身体制御 ＝ ここで完結（低遅延）
                              └─ 会話 ─Funnel─▶ 自宅 Mac Studio（LLM・記憶）
```

ESP32 から見れば**マスタは常に1つ**。MacBook の中で
「これはローカルで処理」「これは自宅に転送」を振り分ける。

### この形の良いところ

- **`questions/stackchan-dual-connection` を回避できる。** 2本張れるか未検証のままでも進める
- 遅延の要るもの（踊り）と重いもの（LLM）が、それぞれ適した場所に置ける
- 自宅が落ちても**踊りは生きる**（当日の保険）
- 家では Mac Studio が両方の役を兼ねるだけ。構成が変わらない

### 役割分担

| | 置くもの | 理由 |
|---|---|---|
| **近いMac**（会場=MacBook / 家=Mac Studio） | 身体制御、踊り、拍の生成、Web操作パネル | 低遅延が要る |
| **遠いMac**（自宅 Mac Studio） | LLM、記憶、カレンダー、家電連携 | 重い・状態を持つ |

## 採用する設定（2026-09-08 決定）

```
websocket.url          = 空（mDNS で同じLANのゲートウェイを探す）
websocket.fallback_url = 自宅の Funnel（wss://<node>.<tailnet>.ts.net/）
```

- 会場 → MacBook を見つける
- 家 → Mac Studio を見つける（**外を回らない**）
- どちらもいない → Funnel で自宅へ

**本体の設定を一度も触らずに、置かれた場所で正しいマスタに繋がる。**
mDNS が効くかどうかが前提なので、**Step 2 の確認項目でこれが最優先**。

### なぜ明示URLではなく mDNS か

家で `fallback_url`（Funnel）に落ちると、**同じLANにいるのに外を一周して戻ってくる**。

```
スタックチャン → 外のインターネット → Funnel → 同じ家の Mac Studio
```

繋がるが数百ms余計に乗る。mDNS ならこのヘアピンが起きない。

---

## 家で両方上がっているとき — Mac Studio が空気を読む

**「両方使う」と「両方が繋ぎ先として名乗る」は別の話。**
リレー構成では、MacBook も Mac Studio も常にフル稼働している。両方でコードを書ける。
競合するのは **スタックチャンが最初にどこへ繋ぎに行くか** の1点だけ。

やりたいことはこれ。

- MacBook が居る → MacBook が繋ぎ先（踊りが低遅延で回る）
- **MacBook が居ない → Mac Studio が繋ぎ先**（外を一周しない）
- どちらも居ない → Funnel で自宅へ

手で切り替えるのではなく、**自動でこうなるようにする。**

### 設計：判断は Mac Studio だけが持つ

| | 役割 | 挙動 |
|---|---|---|
| **MacBook** | `primary` | **何も考えず、無条件で名乗る** |
| **Mac Studio** | `standby` | **MacBook が居ないときだけ名乗る** |

★ **判断を1箇所に集めるのが肝。**
両方が「相手が居るか」を見て譲り合うと、**誰も名乗らない事故**が起きる。
MacBook は空気を読まない。Mac Studio だけが読む。これで決定的になる。

### Mac Studio 側のロジック

```
10秒ごと:
    MacBook のゲートウェイ（macbook.local:8765）に繋がるか試す
      連続3回（=30秒）繋がらない  → 名乗り始める
      連続2回（=20秒）繋がった    → 名乗りを取り下げる
```

判定は **mDNS を見るのではなく TCP で実際に叩く**。
名乗っているだけで死んでいるケースを拾えないため。

### 設定（コードは1つのまま）

```yaml
mdns:
  role: primary        # MacBook
# role: standby        # Mac Studio
  standby:
    probe: macbook.local:8765
    interval_sec: 10
    absent_after: 3    # 連続3回不在で名乗る
    present_after: 2   # 連続2回検知で取り下げる
```

### ヒステリシスを必ず入れる

MacBook のスリープや Wi-Fi の瞬断で、名乗ったり取り下げたりバタつくのが**一番たちが悪い**。
上下で回数を変えてある（不在3回 / 復帰2回）のはそのため。

---

## ⚠️ 知っておくべき挙動：切り替わるのは「次の再接続」

Mac Studio が名乗りを取り下げても、**既に繋がっているセッションは切れない。**

- 勝手に会話が切れない、という意味では**良いこと**
- ただし「MacBook を持って帰ってきたのに、まだ Mac Studio に繋がったまま」になる

**意図的に切り替えたいときはスタックチャンを再起動する**（RST 短押し）。
ESP32 は繋ぎ先が変わったことを知らない。切替のきっかけは接続断だけ。

## 会場ではこの仕組みは発動しない

会場に Mac Studio は居ない（同じLANにいない）ので、MacBook が名乗って終わり。
Mac Studio は Funnel の向こうにいる中継先であって、繋ぎ先候補ではない。

---

## ⚠️ fallback の挙動は3つとも未確認

希望的に見積もると当日事故る。**Step 2 で実測する。**

1. **いつ発動するか** — 起動時に順に試すだけか、接続中に切れても切り替わるか
2. **何秒かかるか** — ライブ中に落ちて、無言の数十秒が発生しないか
3. **自動で戻るか（フェイルバック）** — マスタが復帰しても fallback のままではないか

測り方は3分で終わる。
MacBook を落とす → 何秒で Mac Studio に行くか → MacBook を上げる → 戻るか。

---

## MacBook を止めたとき、何が落ちるか

仕込み③を守っていれば、Mac Studio も**同じゲートウェイを動かしている**。だから：

| | MacBook停止後 | 理由 |
|---|---|---|
| 身体制御（首・表情・LED） | **生きる** | Mac Studio も同じコードを持っている |
| 会話 | **生きる** | むしろ Mac Studio が本籍 |
| **踊り** | **死ぬ** | **DDJ-FLX2 が MacBook に挿さっているから。** MIDI も Link も供給元が消える |

落ちるのは「MacBookの機能」ではなく「**MacBookに物理的に繋がっているもの**」。

Step 2 でファームを焼くときに：

- [ ] `websocket.url` = **空**（mDNS）
- [ ] `websocket.fallback_url` = 自宅の Funnel
- [ ] **mDNS が効くか確認** ← 最優先
- [ ] **fallback の3つの挙動を実測**（発動条件 / 所要時間 / 自動で戻るか）

Step 4 以降：

- [ ] ゲートウェイのコードを1つに保つ
- [ ] `mdns.role` を `primary` / `standby` で持たせる
- [ ] **standby 側（Mac Studio）にだけ自動判定を実装する。** MacBook は無条件で名乗る
- [ ] ヒステリシス（不在3回 / 復帰2回）を必ず入れる
